# 리허설 링크 확인 — 사람이 한 번 누르는 절차

대상: JY · 소요 **3분**(+ 선택 1분) · 준비물 없음 · 관련 [#1131](https://github.com/jayleekr/hypeproof-studio/issues/1131) ·
[#1132](https://github.com/jayleekr/hypeproof-studio/issues/1132)

## 🔴 누르기 전에 — 무엇이 정상인지 먼저 읽어 주세요

> **2번을 눌러도 Studio 안에서는 아무 일도 안 일어나는 것이 정상입니다.**
> 링크를 **받는 코드가 아직 앱에 안 들어갔습니다.** 우리가 보는 것은 그 앞의 네 가지입니다.

출하된 앱(v0.1.56)에서 직접 확인한 사실이다 — 번들된 `hypeproof-chat` 의
`activationEvents` 는 `["onStartupFinished"]` 하나뿐이고, `dist` 안에 `registerUriHandler`
가 **0건**이다. 받는 코드는 [#1132](https://github.com/jayleekr/hypeproof-studio/issues/1132)
에 있고 아직 브랜치다.

### 이 확인이 실제로 답하는 것 — 넷

1. **브라우저가 자체 확인 창을 띄우는가** → "링크 한 번" 이라는 우리 문장이 정확한가
2. **앱이 확인 창을 띄우는가** → 오늘 기계로 잰 것을 실기기로 확인
3. **앱이 뜨는가 · 앞으로 나오는가**, 창이 여럿이면 **어느 창인가**
4. **꺼진 상태와 켜진 상태가 다르게 구는가**

### 이 확인이 답할 수 **없는** 것

- **링크가 확장까지 닿는가.** 받는 코드가 없으니 "안 닿는다" 가 나오는 게 거의 확정이고
  **그건 실패가 아니다.** 이 질문은 **#1132 가 들어간 빌드로 다시 재야** 답이 난다.
- **수업이 실제로 열리는지.** 티켓도 가짜이고 교환 엔드포인트도 아직 없다.

---

브라우저에서 만든 수업을 **링크 한 번으로 앱에서 여는** 것이 C안이다. 기계로 잴 수 있는
데까지는 쟀다. 못 잰 이유는
[실패 경로 문서](../../docs/design/rehearsal-entry-failure-paths.md) §5.3 에 있다 — 합성으로
밀어 넣은 URL 은 `handleProtocolUrl(): not handled` 로 떨어진다. **계측기의 한계이지 제품
결함이 아니다.** 그래서 위 네 가지는 사람이 한 번 눌러야 한다.

---

## 하기 전에 (30초)

```bash
# 1. Studio 를 평소처럼 켜 둔다 (끄지 않는다 — 켜져 있는 상태가 강사의 실제 상황이다)
# 2. 창을 두 개 이상 열어 둔다  ← 질문 2번을 같이 답하려면 필요하다
# 3. 앱 버전을 적어 둔다
defaults read "/Applications/HypeProof Studio.app/Contents/Info" CFBundleShortVersionString
```

**버전이 왜 필요한가**: 지금 출하된 앱에는 **리허설 링크를 받는 코드가 아직 없다**(#1132 는
아직 브랜치에 있다). 그래서 **수업이 열리지 않는 것이 정상**이다. 이 확인의 목적은 수업을
여는 것이 아니라 **링크가 앱까지 가는지**와 **확인 창이 붙는지**를 보는 것이다.

---

## 누르기

```bash
open e2e/observe/rehearsal-link-check.html
```

페이지에 버튼이 둘 있다. **1번을 먼저** 누른다.

| | 무엇 | 정상이면 |
|---|---|---|
| **1번** | 대조군 (`…://file/tmp`) | **경고 창이 뜬다** → 뜨면 **아니오**를 누른다 |
| **2번** | 리허설 링크 (`…://hypeproof.hypeproof-chat/rehearse?ticket=…`) | **확인 창이 안 뜬다.** Studio 안에서 아무 일도 안 나는 것도 정상 |

**1번을 건너뛰면 안 된다.** 1번은 "링크가 앱까지 가는 길이 살아 있다"를 증명하는 자리다.
1번이 안 되면 2번의 "아무 일도 안 났다"는 **제품이 조용한 건지 길이 끊긴 건지 구분이 안 된다.**
오늘 하루 우리를 가장 많이 속인 것이 정확히 그 구분이었다.

### 브라우저가 먼저 묻는 창은 우리가 보려는 것이 아니다

브라우저가 *"HypeProof Studio을(를) 여시겠습니까?"* 를 띄울 수 있다. **그건 브라우저 것이다.**
열기를 누르고 **그다음**에 나오는 것을 본다.
다만 **그 창이 떴다는 사실 자체는 알려 달라** — 강사가 겪는 단계가 하나 느는 것이고,
그것도 결과다.

---

## 결과가 무슨 뜻인가

| 1번 | 2번 | 뜻 | 다음 |
|---|---|---|---|
| 경고 뜸 | 확인 창 **안 뜸** | **원하던 결과.** 길은 살아 있고 리허설 링크에는 확인이 안 붙는다 | "링크 한 번" 확정 |
| 경고 뜸 | 확인 창 **뜸** | 오늘 기계 측정이 **뒤집혔다** | 설계가 바뀌는 게 아니라 **화면 문구가 하나 는다** |
| 경고 **안 뜸** | (무엇이든) | **길이 끊겼다.** 앱 미설치·스킴 미등록 등 | 2번 결과는 읽지 않는다. 아래 "아무 일도 안 났을 때" |

그리고 **2번에서 확인 창 말고 무엇이 보였는지**가 남은 질문 1번의 답이다.

- **앱이 앞으로 나오거나 알림이 하나 떴다** → 링크가 **확장 라우팅까지 닿았다**. (지금 앱엔 받는
  코드가 없으니 "확장을 찾을 수 없다" 류의 말이 나올 수 있다. **그 말이 나오는 것이 좋은 신호다.**)
- **정말 아무 일도 없었다** → 확장까지 안 갔을 수 있다. 아래 절차로 한 번 더 본다.

### 3번 — 앱을 끄고 한 번 더 (1분, 가능하면 해 주세요)

**앱이 꺼져 있을 때와 켜져 있을 때는 앱 안에서 다른 길을 탑니다**(`resolveInitialProtocolUrls`
vs `handleProtocolUrl` — 출하 번들에서 확인). 그래서 같은 링크라도 결과가 다를 수 있습니다.

```
Studio 를 완전히 종료 (⌘Q) → 페이지에서 2번을 다시 누른다
```

**보는 것**: 앱이 뜨는가 · 뜨면서 확인 창이 붙는가 · 그 밖에 무엇이 보이는가.
**강사의 실제 상황은 이쪽일 수도 있습니다** — 수업 만들다가 Studio 를 안 켜 둔 채 링크를
누르는 것이 오히려 흔합니다.

---

## 알려 줄 것 (이게 있어야 한 번 누른 게 헛되지 않는다)

1. 앱 버전 (위에서 적은 것)과 **어느 브라우저로 눌렀는지** (갈래 C 에 걸린다)
2. 1번에서 경고가 **떴는지**
3. 2번에서 확인 창이 **떴는지**
4. 2번에서 **그 밖에 보인 것** — 앱이 앞으로 나왔는지 · 알림이 떴는지 · 아무 일도 없었는지
5. 창이 여럿이었다면 **어느 창이 반응했는지** (마지막에 보던 창인지, 처음 연 창인지)
6. 창이 떴다면 **화면 사진** 한 장
7. 3번(앱 끄고 누르기)을 하셨다면 그 결과 — 앱이 떴는지 · 확인 창이 붙었는지

---

## 아무 일도 안 났을 때만 (추가 2분)

앱이 남기는 기본 로그에는 이 판정에 필요한 줄이 안 들어간다(trace 수준이라). 한 번 더 볼
여유가 있으면 이렇게 한다.

```bash
# Studio 를 완전히 종료한 뒤
"/Applications/HypeProof Studio.app/Contents/MacOS/HypeProof Studio" --log trace
# 창이 뜨면 rehearsal-link-check.html 에서 2번을 다시 누른다
```

그리고 아래 파일을 보내 준다.

```bash
ls -t ~/Library/Application\ Support/HypeProof\ Studio/logs/*/main.log | head -1
```

그 안에 `handleProtocolUrl` 이 들어간 줄만 있으면 충분하다.

```bash
grep handleProtocolUrl "$(ls -t ~/Library/Application\ Support/HypeProof\ Studio/logs/*/main.log | head -1)"
```

- `not handled` 로 끝나면 → 오늘 기계 측정과 **같은 상태**다. 확장까지 가는 경로를 따로 봐야 한다
- 그 줄조차 없으면 → **URL 이 앱에 도달하지 않았다.** 전혀 다른 문제다

---

## 이 확인이 답하지 않는 것 (맨 위에서 이미 읽은 것)

- **링크가 확장까지 닿는지**와 **수업이 열리는지** — 받는 코드가 아직 출하 전이다.
- 오늘 기계로 잰 "확인 창이 안 붙는다"는 **합성 경로** 기준이다. 이 확인은 그것을
  **실제 클릭으로 다시 재는 것**이지 처음 재는 것이 아니다.

---

## 결과를 받으면 무엇이 달라지나 (미리 적어 둔다)

결과를 받고 나서 생각하기 시작하면 하루를 또 쓴다. 세 갈래를 미리 적는다.

### A. 2번에서 앱이 반응했다 (앞으로 나오거나 알림이 떴다)

- [실패 경로 문서](../../docs/design/rehearsal-entry-failure-paths.md) §5.2 의 **⬜ 하나가
  닫힌다** — **어느 창이 받았는지를 알려 준 경우에 한해** "다중 창 수신". 어느 창인지 안
  알려 주면 **안 닫힌다.**
- **"확장까지 닿는가" 는 이 확인으로 안 닫힌다** — 받는 코드가 없으니 여기까지가 한계다.
  다만 앱이 반응했다는 것은 **URL 이 앱에 도달했다**는 뜻이므로, 남은 것은 확장 라우팅 한 겹뿐이다.
- §4 에 **실제 클릭 기준 줄을 추가**한다. 지금 §4 는 합성 경로 기준이고, 이 결과는 그것을
  **대체하는 것이 아니라 한 겹 위에 얹는 것**이다.
- 데모 구성은 그대로다. **"링크 한 번" 이 유지된다.**

### B. 2번이 아무 데도 안 닿았다 (아무 일도 없었다)

**이건 계측기 문제가 아니라 제품 사실이다** — 1번(대조군)이 떴다면 길은 살아 있다는 뜻이므로.

다음 질문은 **이미 정해져 있다**, 순서대로:

1. `--log trace` 에서 `handleProtocolUrl` 줄이 **`not handled`** 로 끝나는가?
   → 그렇다면 오늘 합성 측정과 **같은 상태**이고, **실제 클릭도 확장 URL 을 버린다**는 뜻이다.
2. **3번(앱 끄고 누르기)에서는 달랐는가?** 꺼진 상태는 `resolveInitialProtocolUrls` 를 타므로
   **여기서만 되는 경우가 있을 수 있다.** 되면 강사에게 "앱을 끄고 누르세요" 를 시킬 수는
   없으므로 **앱이 켜져 있을 때의 경로를 따로 풀어야 한다.**
3. 그래도 안 되면 **확장 id 로 라우팅되는 조건**을 봐야 한다 — 출하 앱의 `hypeproof-chat` 은
   `onUri` 활성화 이벤트가 없다(#1132 가 그것을 추가한다). **받는 코드가 들어간 빌드로 다시
   재기 전에는 "제품이 못 한다" 로 결론내지 않는다.**

**데모 구성이 바뀐다**: 링크 한 번이 안 되면 참여 코드 복사가 그대로 남는다. 위클리에 그렇게
말해야 하고, 그 경우 C안의 값은 "왕복 제거" 가 아니라 "리허설이 Studio 에서 돈다는 확정"
쪽으로 줄어든다.

### C. 브라우저가 자체 확인 창을 띄웠다 (A·B 와 별개로 일어날 수 있다)

**실패가 아니다.** 우리 앱의 모달이 아니고, 우리가 끌 수 있는 것도 아니다.

**그러나 사실관계가 바뀐다** — 강사가 겪는 단계가 하나 는다. 위클리에는 이렇게 말한다:

> **"링크 한 번"이 정확히는 "링크 한 번 + 브라우저 확인 한 번"입니다.** 앱이 띄우는 확인은
> 없고(실측), 브라우저가 커스텀 링크를 열 때 자체적으로 묻습니다. 브라우저·설정에 따라
> "항상 허용" 을 한 번 선택하면 이후에는 안 묻습니다. 손으로 코드를 옮기는 것과 비교하면
> 여전히 줄어드는 쪽이지만, **"한 번"이라고 말하면 정확하지 않습니다.**

그리고 **어느 브라우저였는지**를 같이 기록한다 — 브라우저마다 다르고, 워크숍에서 어떤
브라우저를 쓰라고 안내할지에 걸린다.
