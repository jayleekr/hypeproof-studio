## A. 추적 드리프트 — 42/60 (가장 크다)

### 무엇이

요구 문서의 **검증 열**과 검증 문서의 **대상 SX 열**이 42행에서 서로를 가리키지 않는다.

```
SX-09  → SX-T18   그런데 SX-T18 은 SX-11 을 검증한다 (다섯 대화 상황)
                   SX-09(강사 호출)를 실제로 검증하는 것은 SX-T17 이다
SX-17  → SX-T24   그런데 SX-T24 는 SX-17 을 대상으로 적지 않는다
SX-30  → SX-T31   그런데 SX-T31 은 다른 것을 잰다
```

### 어느 쪽이 정본인가 — 알 수 있다

검증 문서는 **세 곳에서 자기 자신과 일치**한다: 행별 `대상 SX` 열, 문서 끝의 `커버리지` 표,
그리고 각 행의 `검사 내용` 산문. 셋이 같은 말을 한다.
요구 문서의 검증 열만 혼자 다르다. → **검증 문서가 정본이다.**

### 왜 위험한가

"SX-30 의 테스트를 쓴다"로 시작한 사람이 엉뚱한 행을 구현한다.
그리고 **"SX-10 검증됨"을 사유 코드를 한 번도 안 본 테스트로 보고**할 수 있다.

### 선택지

| | |
|---|---|
| **(a) 요구 문서의 검증 열을 검증 문서 기준으로 고친다** ← 추천 | 42행. 기계적이다 |
| (b) 검증 문서를 요구에 맞춘다 | 테스트가 하는 일과 이름이 어긋나게 된다 |
| (c) 한쪽에서 생성한다 | 옳지만 지금 할 일은 아니다 |

**추천: (a) + 회귀 방지 한 줄.** `docs-harness/check.py` 에 양방향 대조를 넣는다
(`요구.검증 ⊆ 검증.대상SX`). 지금은 100/100 이 이 드리프트를 그대로 통과시키고,
고쳐 놓아도 **같은 일이 조용히 다시 생긴다.**

## B. 스키마가 요구를 담지 못하는 것 — 5건

각각 "문자 그대로 구현하면 저장할 수 없는 상태"를 요구한다.

### B-1. SX-55 `reflected(skipped)` — 표현 자체가 없다

- 요구: 회고를 **건너뛴 사실만 기록**하고 phase 는 `reflected(skipped)`
- 스키마: `reflected` 로 가는 유일한 전이가 `reflection_submitted` 이벤트를 요구한다.
  건너뛰면 그 이벤트가 없다. phase 타입에 구분 칸도 없다
- **추천**: phase 는 네 값 그대로 두고, **건너뛴 사실을 이벤트로** 남긴다
  (`reflection_skipped` 또는 `reflection_submitted{skipped:true}`).
  "없음"이 아니라 "건너뛰었음"이 기록돼야 SX-26 의 "건너뛴 사실만 기록된다"가 참이 된다

### B-2. SX-23 · SX-45 "이유 미기록" — 저장할 수 없다

- 요구: 선택 이유는 **선택 사항**이고, 비면 decision 이 "이유 미기록"으로 남는다
- 스키마: `decision_revised` 가 유일한 decision kind 인데 `student_text`·`decision.from`·
  `evidence_refs[]` 를 **전부 필수**로 요구한다. 이유 없는 선택은 저장 불가
- 검증 문서 SX-T28 은 **저장된다**는 쪽으로 이미 적혀 있다
- **추천**: `decision_revised` 의 `student_text` 를 선택으로 내리고 "이유 미기록"을
  UI 라벨로 둔다. 아홉 번째 kind 를 만들지 않는다(게이트·서랍·fixture 가 전부 배워야 한다)

### B-3. SX-24 팀 기여 — 칸이 없고 allowlist 가 닫혀 있다

- 요구: `artifact_after` 와 Decision 이 팀원 식별자를 갖는다
- 스키마: `artifact_after` 는 **64자 16진수 sha256** 이다. 식별자를 실을 수 없다.
  `/2` 키 allowlist 는 닫혀 있고 팀 정체성이 시스템 어디에도 없다
- **추천**: 지금은 **"팀원 미구분"** 으로 두고(요구가 균등 분배를 이미 금지한다),
  칸 신설은 MC-39 와 함께. 이 결정이 P1 에서 SX-24 를 뺀 이유이기도 하다

### B-4. SX-44 `teacher_state` — 이벤트 필드가 아니다

- 요구: 이벤트 저장 계약의 **필드 7개** 중 하나로 적혀 있고, SX-T53 이 "각 필드 누락 → 거절"을 통과 조건으로 삼는다
- 설계: `teacher_state` 는 이벤트에 **저장하지 않는다.** 별도 record 에서 최신값을 읽어 계산한다
- 코드가 이미 설계를 따랐다 — `LEARNING_EVENT_KEYS` 에 없어서 실으면 거절된다
- **추천**: 요구에서 이 필드를 7개 목록에서 빼고 "계산되는 값"으로 옮긴다. SX-T53 도 같이

### B-5. SX-14 "Service 가 거부한다" — 그런 지점이 없다

- 요구 부정 조건: "키보드나 API 직접 호출로 완료 이벤트를 보내도 **Service 가** criterion_set 없이는 거부한다"
- 실제: Service 에 과제 상태도 완료 엔드포인트도 **없다.** `/2` 배치를 보는 유일한 라우트는
  읽기 전용 `POST /observations/validate` 다
- 어젯밤 내가 **호스트에** 재판정(`acceptSubmit`)을 넣었다 — 요구가 말한 곳이 아니다
- **추천**: 요구를 **"호스트가 거부한다"** 로 고친다. 오늘의 신뢰 경계가 거기다.
  Service 강제는 MC-39(원격 제출) 이후에나 의미가 있다

## C. 요구끼리 충돌 — 4건

### C-1. SX-07 ↔ SX-08 (개입 상한 vs 사다리)

- SX-07: 단계당 **자발적 개입 1회** 상한
- SX-08: 같은 단계에서 **반복 실패**하면 사다리를 올라간다 — 학생이 요청하지 않은 개입이 여러 번
- **추천**: SX-07 의 상한을 **"학생이 막히지 않은 상태의 개입"** 으로 좁힌다.
  SX-07 이 막으려는 것은 불쑥 칭찬·잡담이지(그 부정문이 그렇게 적혀 있다) 막힌 학생을 돕는 것이 아니다

### C-2. SX-30 ↔ SX-37 (첫 화면 숫자 금지 vs 2번 블록이 숫자를 요구)

- SX-30 부정: 첫 뷰포트에 **숫자 하나라도** 있으면 실패
- SX-37: 2번 블록("아직 드물게 본 행동")이 첫 화면에 펼쳐져 있고, 그 문장 형식이 **분모·분자를 의무화**한다
- 문서 셋이 각자 다른 쪽을 골랐다(설계 와이어프레임은 숫자를 뺐고, SX-T39 는 숫자를 요구한다)
- **추천**: INT-SX-07 이 금지하는 것은 **점수**이지 "세어 본 사실"이 아니다.
  원문 §12 의 예시 문장이 그 숫자를 갖고 있고, 빼면 "드물다"가 근거 없는 주장이 된다.
  → SX-30 의 부정을 "점수·등급·퍼센트"로 좁히고 SX-37 의 숫자는 남긴다

### C-3. SX-02 ↔ SX-56 (action 4개 이상 거부 vs 단계가 action)

- SX-02: action 이 4개 이상인 설계 파일은 **검증에서 거부**
- SX-56: 단계별 action 의 유일한 집이 설계 파일이고, 6주 fixture 중 5개가 6단계다
- **추천**: 단계와 action 을 분리한다. "한 화면에 보이는 action 3개"는 **표시 규칙**이지
  파일 검증 규칙이 아니다. 코드도 이미 그렇게 갔다(`MAX_ACTIONS=3`, 현재 단계부터 slice)

### C-4. SX-17 ↔ 설계 3주차 예시 (서랍 기본 닫힘 vs 첫 단계가 `criterion_form`)

- SX-17 부정: 서랍이 **작업 시작 시 자동으로 열리면 실패**
- 설계 3주차 예시: 첫 단계가 `"ui": "criterion_form"` — 그 주를 열면 서랍이 자동으로 열린다
- **추천**: SX-17 의 부정을 **"학생이 열지 않았는데 반복해서 열리면 실패"** 로 좁힌다.
  INT-SX-03 의 "필요 시 노출"은 조르지 말라는 뜻이지, 그 단계가 받으려는 폼을 숨기라는 뜻이 아니다

## D. enum 불일치 — 1건

**SX-44 가 같은 필드에 두 enum 을 적는다.** 새 4값 enum 의 학생 값은 `student`,
보존된 legacy 2값 enum 의 학생 값은 `user`. 다섯 개의 하위 행이 첫 번째 어휘로 쓰여 있다.

- **추천**: `user` 로 통일한다. 설계가 이유를 이미 적었고("`/1`의 값을 유지해 재매핑을 피한다"),
  MC-T01 의 golden fixture 가 `/1` 위에 **바이트 단위로** 고정돼 있어 `student` 로 가면 그 fixture 가 움직인다

## E. 검증 문서 자체의 색인 드리프트

`SX-T02·03·14·17·20·21·24·27·31·34·37·39·52~59` — 검증 문서의 **층·명령 색인 표**가
자기 **행별 층/명령 열**과 약 30곳에서 다르다. 색인은 "이 조각을 어떤 명령으로 돌리나"를
정하는 표라서, 틀리면 엉뚱한 명령을 돌린다.

- **추천**: 행별 열이 정본(각 테스트 작성자가 실제로 쓰는 칸이다). 색인을 거기서 생성한다

## 반박으로 **기각된** 45건에 대해

감사자가 올렸는데 반박자가 문서를 열어 보고 무효로 판정한 것이 45건이다. 대부분:

- 같은 문서 **다른 절에 해소 문장**이 있는데 감사자가 못 봤다
- 한 개념을 **두 추상 수준**에서 기술한 것을 모순으로 읽었다
- 인용이 부정확했다

**이 45건을 Jay 에게 올리지 않는다.** 판정서 없이 그대로 올렸으면 목록이 77건이 되고
그중 절반이 헛것이었을 것이다. 반박 단계의 값이 이것이다.
