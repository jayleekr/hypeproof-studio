## 치기 전에 (매번)

```bash
# 1. 세션이 열려 있는지 — 안 열려 있으면 코치가 빈 응답만 낸다
curl -s -H "Authorization: Bearer $ISSUER" \
  https://api.hypeproof-ai.xyz/admin/cohorts/boah-dental-2026-a/state | jq .session

# 2. 워크스페이스를 비운다 — 남아 있으면 "만든 것"과 "있던 것"이 구분 안 된다
rm -rf ~/HypeProofClinic/*

# 3. 앱을 디버깅 포트로 띄우고 관측기를 붙인다
open -a "HypeProof Studio" --args --remote-debugging-port=9333
HPS_CDP_PORT=9333 node e2e/observe/watch.mjs
```

`session: null` 이면 채팅이 `403` 으로 막힌다. `/console` 에서 **원장 웹사이트
카피클론** 트랙을 연다. `hypeproof-ai.xyz/adult-edu/…` 는 학생용 안내 페이지라
거기서는 세션이 열리지 않는다.

## 커맨드 1 — 참고 사이트만 주고 초안

> `https://boaclinic.com/ 이거대로 치과 웹사이트 만들어줘`

**큐시트**: 19:30–19:45 Reference First
**의도**: URL 하나로 초안이 나오는가. 스크린샷을 요구하지 않는가.

### 볼 것

| | 정상 | 이상하면 |
|---|---|---|
| 첫 동작 | `browser_open(boaclinic.com)` → `browser_read` | 스크린샷을 붙여 달라고 되물으면 프롬프트 회귀 |
| 저장 경로 | `Write(index.html)` — **첫 시도에 성공** | `Write(/Users/workspace/…)` 처럼 지어낸 경로가 뜨면 작업 폴더가 안 전달된 것 |
| 탐색 | `find` · `pwd` · `Glob` **0회** | 나오면 위와 같은 원인 |
| 산출물 | `~/HypeProofClinic/index.html` 실재 | 채팅에 ` ```html ` 펜스를 쏟아내면 낡은 프롬프트 |

### 실측 기준선

```
v0.1.32   438s · 툴 17회 · 승인 1회 · index.html 21.6KB   ("뼈대만" 붙였을 때)
v0.1.30   535s = 코치 355s + 승인대기 180s · 툴 5회 · 24.9KB
v0.1.28   같은 요청에서 지어낸 경로로 Write 실패 → 164초 재생성
```

`"뼈대만"` 을 붙이면 산출물이 눈에 띄게 작아진다 — 크기는 프롬프트로 제어된다.

승인은 **처음 `boaclinic.com` 열 때 1회**만 뜬다(오리진 기억). 「이 사이트는 항상
허용」을 누르면 이후 서브페이지는 안 묻는다.

## 커맨드 2 — 콘텐츠 주입 + 인수인계 문서

> ```
> 실제 보아치과의 핵심 컨텐츠는
> 1. About us
> 2. 첨단 디지털 클리닉 (첨단기술 강조)
> 3. 평생 예방관리 클리닉 (예방의학 타겟)
> 4. 어르신 보험 임플란트 (실버 타겟)
> 이다 이것들을 보아치과 웹사이트에서 내용부분을 가져와서 agent.md 로 저장하고
> 이 md 파일을 보고 우리 웹사이트를 고쳐보자.
> ```

**큐시트**: 19:45–20:05 Context Engineering (+ 결과물 4 `agent.md`)
**의도**: 컨텍스트를 주면 결과가 **눈에 띄게** 달라지는가. 그리고 그 컨텍스트가
문서로 남아 다음 AI 에게 넘어가는가.

### 볼 것

| | 정상 | 이상하면 |
|---|---|---|
| 수집 | 서브페이지를 실제로 열어 읽음 (`browser_open` → `browser_read` 반복) | 원본을 안 보고 지어내면 R0 문제 |
| `agent.md` | **파일로** 저장 (`Write(agent.md)`) | ` ```agent-md ` 펜스로 나오면 낡은 프롬프트 |
| 내용 | 4개 카테고리가 실제로 담김 | `grep -c "About\|디지털\|예방\|임플란트" agent.md` |
| 수정 방식 | `Read` 한 번 → `Edit` 여러 번 | 매번 `Write` 로 전체 재생성하면 느리고 위험 |
| 반영 | `index.html` 이 실제로 바뀜 | 크기·mtime 확인 |

### 실측 기준선

```
v0.1.32   453s · 툴 52회 · 실패 1 · 승인 0회 · Read 7회 전부 범위지정
v0.1.31   463s · 툴 21회 · 실패 0 · 승인 0회
v0.1.30   403s = 코치 259s + 승인대기 144s · 툴 37회 · 실패 1
v0.1.29   547s = 코치 431s + 승인대기 116s · 툴 52회
v0.1.28   같은 요청에서 20턴 예산 소진으로 **두 번 사망**
```

`Edit` 이 여러 번 도는 것은 정상이다 — 전체 재생성이 아니라 부분 수정이라는 뜻이다.

### 알려진 실패 (정상 복구)

```
Write(index.html) — 실패: File has not been read yet
  → SDK 안전장치. 코치가 Read 후 재시도하면 정상. 다만 100초쯤 잡아먹는다.

browser_click(e7) — 실패: e7를 찾을 수 없어요
  → 코치가 페이지 이동 후 옛 ref 를 쓴 것. browser_read 다시 하면 성공.
```

## 커맨드 3 — 루브릭 세우고 될 때까지 (**빠져 있던 블록**)

> `이 화면 평가 기준을 먼저 만들고, 직접 열어서 검사한 다음, 기준에 못 미치는 걸 찾아서 고쳐줘. 될 때까지 반복해.`

**큐시트**: 20:05–20:35 Loop Engineering — *"핵심은 될 때까지 반복시키는 것"*
**의도**: 검사 → 수정 → **재검사** 가 실제로 도는가. 말로만 "고쳤습니다" 가 아닌가.

큐시트에서 가장 긴 블록(30분)이고 척추인데, 초안 커맨드 목록에는 없었다.

### 볼 것

| | 정상 | 이상하면 |
|---|---|---|
| 기준 수립 | 코치가 평가 항목을 **먼저** 제시 | 기준 없이 바로 고치면 루프가 아니다 |
| 검사 | `live_preview_start` → `browser_screenshot` → `browser_read` | 검사 없이 "고쳤습니다" 면 R0 계열 |
| 수정 | `Edit` (부분) | 전체 재생성이면 느리고 다른 데가 조용히 바뀐다 |
| **재검사** | 고친 뒤 다시 스크린샷/read | **이게 없으면 루프가 닫히지 않은 것** |
| 반복 | 2회 이상 순환 | 한 바퀴만 돌고 끝나면 "될 때까지" 가 아니다 |

### 실측 기준선 (v0.1.32, 2026-07-27)

```
510s · 툴 22회 (Edit 12 · screenshot 4) · 실패 0 · 승인 0회
수정 → 검사 를 3바퀴 돌고 닫힘
100점을 요구받고 83점이라고 보고 (R0 통과)
```

`browser_click` 이 여기서 가장 많이 쓰인다(햄버거 메뉴·링크가 실제로 되는지).
클릭 전에 `browser_read` 가 선행하는지 보라 — 페이지가 바뀐 뒤 옛 ref 를 쓰면 실패한다.

## 커맨드 4 — 저장소 + 배포

> `깃헙에 올리고 배포해줘`

**큐시트**: 20:35–20:58 최종안 고정 (결과물 2 배포 URL, 결과물 3 GitHub 저장소)
**의도**: 참가자가 git 을 몰라도 저장소와 공개 주소가 생기는가.

### 볼 것

| | 정상 | 이상하면 |
|---|---|---|
| `git` 호출 | **0회** | `git` 이 불리면 CLT 설치창(2GB)이 뜬다 — 회차가 거기서 끝난다 |
| 도구 | `gh` 를 받아서 씀 (`curl` → `unzip`) | |
| 로그인 | device flow — 참가자가 코드 입력 | |
| 저장소 | `gh api repos/{owner}/{repo}/contents` 로 실재 확인 | 확인 없이 주소를 말하면 R0 |
| 배포 | GitHub Pages(정적) — `curl -sIL` 로 **200 확인 후** 주소 발설 | 404 구간에서 재배포를 시도하면 안 된다. 첫 배포는 몇 분 걸린다 |
| 터널로 갔다면 | **임시임을 명시** | 영구 주소로 안내하면 참가자가 집에서 404 를 본다 |

### 실측 기준선 (v0.1.32, 2026-07-27)

```
저장소  30s · git 호출 0회 · gh api 로 실재 확인
배포    82s · Pages build_type=workflow · curl -sIL 로 200 확인 후 주소 발설
        404 구간에서 재배포 대신 12회 폴링으로 대기

#500 이후 추가로 볼 것: 코치가 `PUT /pages` **직후에** 워크플로 파일을 올리는가.
그러면 `configure-pages` 가 `HttpError: Not Found` 로 죽는다(프로비저닝 비동기).
`build_type=workflow` 를 확인하는 대기 루프가 업로드보다 **먼저** 나와야 한다.
```

**돌릴 때마다 공개 저장소가 생긴다** — 테스트 계정이나 정리 계획을 정하고 시작한다.
(07-27 검증본: `ico1036/boa-dental`)

## 매 커맨드 공통 — 관측기가 뽑아 주는 것

```
■ 턴 N 종료 — 403s (코치 259s + 승인대기 144s) · 🔧37 ⚠️1 · 승인 6회 · 파일 2
```

- **코치 시간 vs 승인 대기**를 갈라 본다. 느린 게 제품인지 사람인지 구분된다.
- **승인 횟수**는 줄어드는 방향이어야 한다. 늘었으면 정책이 되돌아간 것이다.
- **⚠️ 옆의 사유**를 읽는다. 사유 없이 실패만 보이면 그건 관측기 문제다.

기록은 `e2e/observe/runs/session.jsonl` 에 남는다. 회차별로
`HPS_OBSERVE_OUT` 을 갈라 두면 비교가 쉽다.
