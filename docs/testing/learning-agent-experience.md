## 실행 준비와 증거 계약

1. 기존 [native Studio 노트북 실행 절차](https://github.com/jayleekr/hypeproof-studio/blob/7f41c104d9201765a14d8030cca787b612d04794/docs/testing/studio-native-trial-laptop.md)를 먼저 확인한다.
   해당 스크립트를 AE 테스트 실행기라고 부르지 않는다. 설치 앱 확인·실제 모델 연결·증거 디렉터리 관행을 재사용하고 구현 시 소유 테스트에 연결한다.
2. 강사 2명·성인 학생 2명·서로 다른 수업/프로젝트, 합성 병원 자료, 정상/결함 예제,
   독립 공지 과제를 준비한다. 자료 A/B는 해시로 고정하고 공유·제거 시험에는 합성 식별 표식을 사용한다.
3. App·Service·Module·SDK/모델·OS·시작 파일·정책·도움 방식과 실행 시각을 기록한다.
   실제 App에 주입된 확장 버전도 확인한다. 운영 학생 자격과 개인 대화는 fixture로 사용하지 않는다.
4. 먼저 정상 동작과 심은 결함으로 검사기를 점검한다. UI 캡처·실제 도구 이벤트·파일 읽기·
   요청 payload 중 해당 주장에 필요한 증거를 확보한다. AI의 성공 문장을 도구 실행 근거로 쓰지 않는다.
5. 시나리오별 PASS/FAIL/BLOCKED/NOT RUN, 실행 명령·commit·환경·관측·증거 경로를 남긴다.
   미구현은 NOT RUN, 필요한 실기 환경 부재는 BLOCKED 사유로 기록하며 통과 분모에서 숨기지 않는다.

요청 payload 검사는 통제된 합성 자료에서만 수행하고 인증 헤더는 수집하지 않는다.
평가 원문 전송과 강사 공유는 기존의 개별 확인을 유지한다. 실패 시 계측기와 제품 결함을
구분하고 영향받는 시나리오를 수정된 검사기로 재실행한다.

운영 규모 목표: 30명 파일럿 후 100명 합성 부하. p50/p95 응답 시작·작업 완료·도움 대기,

기술 측정의 분모는 요청·작업 시도·참여자 중 무엇인지 명시한다. 전체 참여자 수와
완료·중단·연결 실패·관측 거절을 함께 보고하고 미관찰을 0점이나 성공으로 채우지 않는다.
작업 시간은 모델 대기·학생 판단·장애 복구로 분리하고 단순히 빨라진 것을 학습 개선으로 해석하지 않는다.
기존 자료 선택·발화를 근거로 삼아 기록 입력 부담도 관찰한다.

학습자 인터뷰는 “무엇이 바뀌었나 / 무엇을 직접 결정했나 / 아직 확인하지 않은 것은 무엇인가 /
다음에는 혼자 할 일과 맡길 일은 무엇인가”를 중심으로 한다. 제품 비교의 작은 표본으로 효과 크기를 확정하지 않는다.
원래 과제와 전이 과제, 도움 조건과 수행 순서를 기록한다. 도움 기록이 없으면 독립 수행을 추정하지 않는다.

회고에는 가설, 버전/조건, 동의된 근거, 혼동 가능성, 유지/수정/보류, 다음 담당·재검증을 적는다.
원문 제공을 거절한 학생도 기본 수업에 참여한다. 새 연구 수집이나 보관 기한 변경은 이 계획만으로 시작하지 않는다.

Lab §11 연구 질문을 관측으로 바꿀 때 기술 성공률·작업 시간·모델 비용과 인간의 기준 선택·반례 탐색·
확신 조절·위임 이유를 별도로 보고한다. 같은 도메인의 작은 변경과 다른 도메인의 전이를 구분한다.
후속 관찰 시점과 비교 조건은 실습 전에 정하며 한 번의 관찰을 장기 유지 증거로 쓰지 않는다.
AI 도움을 제거하면 필요한 지원까지 사라지는 사람에게 강제 무도움 조건을 배정하지 않는다.
인간 피드백의 효과와 여러 모델의 효과도 별도 조건으로 기록한다. 각 결과는 성장·무변화·약화 가설을
