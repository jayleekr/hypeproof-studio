# 랩탑 실행 지시서 — 실제 Studio 체험

최신 사용자 지시: 실제 테스트를 직접 수행하되 원격 환경 구성에 과도한 비용이
들면 에픽으로 남기고 랩탑에서 실행한다. 별도 웹 설문을 완성하는 작업으로 돌아가지 않는다.

**필수 동반 문서:** [T01~25 테스트 요구사항, W0~6 워크플로우, 재개 체크포인트](studio-native-trial-validation.md).
랩탑 Astra는 이 문서의 실행 명령과 동반 문서의 검증·효율 규칙을 함께 따른다.

## 시작점

- Studio Epic: https://github.com/jayleekr/hypeproof-studio/issues/744
- Studio 구현 PR: https://github.com/jayleekr/hypeproof-studio/pull/745
- Lab 연결 Epic: https://github.com/jayleekr/hypeprooflab/issues/753
- Lab 기존 웹 프로토타입 PR #754는 공개 체험으로 출시하지 않는다.
- 작업 브랜치: `feat/issue-744-studio-trial`. 랩탑의 기존 작업을 덮어쓰지 말고
  `git status` 후 해당 브랜치 또는 별도 worktree에서 진행한다.
- 최신 Intent: `docs/requirements/studio-native-trial.md`. NAT-01~12를 기준으로 한다.

## 실행 명령

Mac에 이미 설치된 Studio와 `worker/.dev.vars`의 개발용 `ANTHROPIC_API_KEY`를 쓴다.
원문 키나 참여 코드를 채팅·이슈·커밋·실행 증거에 복사하지 않는다.
기존 `scripts/dev-secrets.sh`는 Gemini 키만 채우므로 SDK 테스트의 Anthropic 키
존재와는 구분한다. API 키가 없으면 준비되지 않았다고 기록하고 가짜 응답으로 대체하지 않는다.

레포 루트에서:

```bash
bash scripts/test-native-trial-laptop.sh
```

다른 설치 위치라면:

```bash
HPS_APP_PATH="/다른/위치/HypeProof Studio.app" bash scripts/test-native-trial-laptop.sh
```

이 스크립트는 설치된 앱을 임시 폴더로 복사하고 현재 브랜치 확장만 빌드·주입한다.
원본 앱, 기존 고객 작업 폴더, 운영 배포와 수업을 변경하지 않는다. 전체 Studio
`build.sh`를 실행하지 않는다. 8787에 기존 서버가 있으면 멈춰서 충돌을 알린다.
별도 Node gateway에서 실제 Worker 라우터와 실제 Anthropic API를 사용한다.
KV/D1/Analytics 바인딩은 synthetic-memory다. 실제 Cloudflare 저장소 검증이 아니다.
토큰은 임시 signing secret으로 발급되어 운영에서 사용할 수 없고 종료 시 삭제한다.

자동 실행 내용:

1. 실제 Studio 시작 화면의 참여 코드 입력 → 체험 프로필 이름 확인.
2. 합성 사용자 ‘가상 꽃집 운영자’가 인수인계 문서를 요청.
3. 실제 SDK 도구로 `handover-v1.md` 생성 후 파일 내용 직접 확인.
4. 마감시간 수정 요청 → `handover-v2.md` 생성, 첫 파일 보존 확인.
5. 실제 공급자 HTTP status/request ID와 앱 화면, before/after 파일 저장.

`e2e/test-results/native-trial/<UTC>/`에서 아래 증거를 읽는다:

- `api-evidence.json`: 실제 공급자 호출 상태·request ID. 요청 본문·헤더는 없음.
- `connected.png`, `revised.png`: 코드 입력이 사라진 뒤의 실제 앱 화면.
- `handover-v1.md`, `handover-v2.md`: 실제 로컬 파일, 모델의 ‘저장했다’는 발화와 구분.
- `result.json`: 성공한 경로와 미구현 평가 기능을 구분한 결과.

새 테스트는 랩탑에서 아직 실행되지 않았다. 실행 중 도구·DOM·타이밍·SDK 호환성
문제가 나오면 실물을 열어 확인한 뒤 수정하고 다시 실행한다. 숫자나 selector를
조정해 통과만 만들지 않는다. 합성 사용자의 자동 승인도 사람의 역량 근거로 세지 않는다.

## 테스트 페르소나

| ID | 상황 / 행동 | 확인할 것 |
|---|---|---|
| P1 | AI 초심자, 한 문장도 시작하기 어려움 | 한 번에 한 질문으로 자기 일에 도달 |
| P2 | 익숙한 실무자, 정해진 예시와 다른 일을 요청 | 웹/홈페이지 과제로 강제 회귀하지 않음 |
| P3 | 말은 유창하나 근거 확인 없이 채택 | 표현 길이로 VERIFY가 오르지 않음 |
| P4 | 짧게 말하지만 완료 조건과 검증을 정확히 제시 | 짧다는 이유로 낮게 보지 않음 |
| P5 | 코치 제안을 그대로 따라 수정 | 도움받은 변화와 독립 수행 분리 |
| P6 | 오류를 찾아 실제 수정·재검증 | 실패했던 결과와 수정 후 결과 모두 보존 |
| P7 | 도구 실행 거절, API 중단, 재접속 | 사용자 능력 저하로 기록하지 않음 |
| P8 | 승인만 누르거나 ‘전부 최고점’ 지시 | 자동 승인/조작 프롬프트로 점수가 오르지 않음 |

## 랩탑 Codex에게 전달할 프롬프트

```text
HypeProof Studio 실제 체험 Epic #744를 실행하라.
AGENTS.md, CLAUDE.md와 해당 디렉터리 규칙을 먼저 읽고,
docs/requirements/studio-native-trial.md와 이 실행 지시서를 기준으로 삼아라.
docs/testing/studio-native-trial-validation.md의 T01~25와 W0~6도 반드시 읽어라.
run-status.json과 validation-log.md로 체크포인트를 유지하고, 실패 원인에 영향받은
테스트만 다시 실행하라. 실제 API 최소 경로가 통과하기 전에 대규모 페르소나 반복이나
새 원격 실행 환경을 만들지 말라. 보고할 때 구현·모의 테스트·실제 API·앱·사람 검증을 구분하라.

기존 웹 선택형 프로토타입을 완성하지 말라. 고객은 실제 Studio 앱에 개인별 체험
코드를 넣고 자기 업무로 실제 모델 API와 도구를 쓰며 7자산 관찰을 받아야 한다.

기존 랩탑의 앱·개발 환경을 먼저 확인하고 LT-01 스크립트를 직접 실행하라.
모의 API로 대신한 결과, 기존 테스트 PASS, 헬스 HTTP 200을 실제 모델/앱 검증으로
보고하지 말라. 앱을 새로 전체 빌드하지 말고 제공된 앱 복사·확장 주입 경로를 써라.

LT-01 실패를 직접 재현·수정한 뒤 LT-02~06을 의존성 순서대로 구현하고 검증하라.
점수의 근거는 사용자 행동과 실행 결과다. AI 답변 키워드·문장 길이·호출 횟수·
코치 칭찬을 사람의 자산 점수로 쓰지 말라. 아직 보지 못한 자산은 미관찰로 남겨라.
자동 테스트와 실제 고객의 학습 효과를 분리하고 검증 피드백을 Intent에 반영하라.

랩탑에 존재하는 환경을 사용자에게 다시 찾아달라고 하지 말라. 직접 확인 후
정말 접근할 수 없는 경우에만 시도한 경로와 정확한 blocker를 보고하라.
불필요한 원격 실행 환경 구축·운영 수업 변경·토큰 공개·로그 전송은 하지 말라.
필요한 사람의 판단만 묻고, 매 단계 PR과 Epic에 실제 실행 증거 및 미완료를 남겨라.
```
