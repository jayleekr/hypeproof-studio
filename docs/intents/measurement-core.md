# 공통 측정 코어 — Product Intent

상태: 개발 기준 제안, 구현·실사용 검증 전. 2026-09-13.
Owner: jayleekr (기존 Studio capability 도메인). [Epic #1020](https://github.com/jayleekr/hypeproof-studio/issues/1020), [기준 정의 #1021](https://github.com/jayleekr/hypeproof-studio/issues/1021).

## Product Intent

**Jay가 Studio, Claude Code, Codex에서 실제 제품을 만드는 동안, 자신이 내린 판단과 AI에 맡긴 일, 확인한 결과를 근거와 함께 돌아보고 다음 작업을 개선할 수 있게 한다. 이 경험을 만드는 관찰·근거·해석 기능을 Studio에서 공통 코어로 분리하여, 같은 기록이 사용 도구와 Asset 모델이 바뀌어도 이어지고 재검토될 수 있게 한다.**

이 문서의 Intent는 개발하려는 제품의 목적이다. 후보 역량 모델의 `INTENT` 항목과 다르다. 상위 [Product Intent](../PRODUCT-INTENT.md)의 Useful work first, Human judgment stays visible, Evidence over claims, Capability models are hypotheses 원칙을 구체화한다. Lab 철학과 Asset 정의의 소유권은 옮기지 않는다.

## 먼저 해결할 문제

Studio 내부에 있는 측정 기능만으로는 다른 AI 도구에서 수행한 실제 작업을 같은 기준으로 돌아보기 어렵다. 별도 과제만 평가하면 평소의 판단과 재사용·수정·실패를 충분히 관찰하기 어렵다. 반대로 대화 로그를 많이 모으는 것만으로는 누가 무엇을 판단했고 그 결과가 유용했는지 알 수 없다.

첫 제품은 **Jay의 실제 작업을 위한 도구**다. 관찰된 판단에 연결된 작업 카드가 사용자 가치이고, 검토된 증거와 반례가 연구 입력이다. 첫 데이터가 Jay 한 명에게서 나왔다는 사실을 유지한다. 사람 전체에 대한 역량 지수나 채용·교육 인증으로 확대하지 않는다.

## 세 가지 Intent

| ID | 의도 | 성공을 관찰하는 방법 |
|---|---|---|
| INT-MC-01 | 일상 작업을 방해하지 않으면서, 목적·판단·위임·검증·결과의 연결을 Jay가 확인하고 다음 작업에 사용할 수 있게 한다. | 실제 작업의 카드에서 적어도 하나의 근거와 해석을 Jay가 검토하고, 다음 작업에서 확인할 개선점을 고른다. 선택 사실과 실제 개선 효과는 별개로 기록한다. |
| INT-MC-02 | Studio의 측정 기능을 독립 실행 가능한 공통 코어로 분리하고 세 호스트가 같은 계약을 사용하게 한다. | 같은 정규화 입력은 호스트와 무관하게 같은 근거 연결·검증 결과를 낸다. Studio도 공통 구현을 호출하며, Claude Code·Codex는 Studio·Chalk 실행 없이 작동한다. |
| INT-MC-03 | 원래의 관찰과 나중의 해석을 구분해, 사람의 작업 개선과 Asset 모델 개선이 서로 검증 가능한 형태로 연결되게 한다. | 기존 해석을 보존한 재해석, 미분류 사례·반례, 모델 변경 이유·검증 계획을 추적한다. 새 이름이나 점수 증가를 개선의 증거로 간주하지 않는다. |

## 첫 사용자와 첫 장면

첫 사용자는 Jay, 첫 환경은 Jay의 macOS와 명시적으로 등록한 HypeProof 작업 폴더다. Claude Code와 Codex의 실제 설치 버전을 기록하고 순차 검증한다. Studio는 기존 앱의 측정 경로를 같은 코어로 연결한다. 전체 Studio 앱 신규 빌드나 운영 Worker 배포는 이 dogfood의 선행 조건이 아니다.

1. Jay가 플러그인을 설치하고 기록할 프로젝트를 선택한다. 현재 기록 범위와 정상 연결 여부를 확인한다.
2. 실제 할 일을 시작한다. 이미 말한 목적을 재입력하지 않는다. 필요할 때만 작업 제목이나 기존 이슈를 연결한다.
3. 평소처럼 AI와 작업한다. 도구를 바꾸거나 세션을 다시 열어도 명시적으로 같은 작업에 연결할 수 있다.
4. 작업을 마치거나 중간 점검할 때, 결과물·주요 판단·검증 결과·미확인 사항을 보여주는 작업 카드를 연다. 근거를 열고 틀린 해석이나 공유 범위를 고친다.
5. Jay가 선택한 내용을 로컬 연구 보관함에 제출하고 접수 기록을 확인한다. 로컬 보관과 원격 서버 접수를 혼동하지 않는다.
6. 다음 작업에서 확인할 개선점 하나를 고른다. 이후 관찰로 시도·결과·미확인을 구분한다. 반복되는 미분류·반례는 Asset 연구 검토로 보낸다.

## 첫 버전의 성공과 실패

첫 버전의 성공은 설치 가능 여부에 그치지 않는다. 세 호스트가 동일 코어를 사용하고, Jay가 Claude Code·Codex의 실제 작업을 검토·제출하며, 후속 작업에서 개선점의 적용 여부를 확인해야 한다. [수용 계획](../testing/measurement-core.md)의 최소 사례는 제품 경로를 확인하기 위한 것이며 통계적 타당성 표본이 아니다.

다음이면 설계를 다시 본다: Jay가 가치를 얻기 전에 보고서를 반복 작성해야 함; 의미 있는 판단보다 로그량만 증가함; 코어를 복제해 호스트별 해석이 갈라짐; 실패·누락이 좋은 점수로 보임; 잘못된 해석을 수정할 수 없음; 제출만 쌓이고 실제 작업 또는 모델 검토로 돌아오지 않음.

## 범위와 단계

- **P0 — Jay dogfood:** 공통 코어 추출, Studio 재연결, Claude Code·Codex 어댑터, 로컬 검토·제출, 버전·누락·데이터 통제, 실제 사용 수용.
- **P1 — 내부 멤버 제품:** 인증된 팀 수집, 멤버별 권한, 지원·삭제 정책, 업무 완료에 증거 제출을 연결하는 운영 규칙. P0 사용성·수집 신뢰성 검토 후 적용한다.
- **P2 — 연구 운영:** 검토된 사례와 반례로 Asset 모델 비교·개정·재평가. 기본 버전 구분과 미분류 기록은 P0부터 필요하다.

전 멤버 강제 설치, 원격 자동 업로드, 숫자 종합점수, 다른 사람과의 순위, 모든 앱 대화 감시, ChatGPT 일반 웹 UI 확장은 P0에 포함하지 않는다. 여기서 Codex와 일반 ChatGPT 앱은 같은 호스트로 취급하지 않는다.
