# Studio 개인 체험 요구사항

상태: #745에서 개인 권한·호스트 기록·평가 API·결과 화면을 구현했고, #757에서 시작 버튼의 세션 재확인과 코치 진입을 수정했다. 실제 API·Mac 검증 범위는 [실행 기록](../testing/studio-native-trial-results-2026-09-08.md)을 따른다.
#758은 [화면별 조작 요구사항](studio-native-trial-ux.md)과 [UX 테스트](../testing/studio-native-trial-ux.md)를 추가한다. 머지, 배포, 설치본 검증, 사람 파일럿은 각각 기록한다.

## Product Intent와 체험 범위

상위 [Product Intent](../PRODUCT-INTENT.md)의 Useful work first, Human judgment stays visible,
Minimum necessary intervention을 이 체험의 행동 계약으로 구체화한다.
Human Asset `INTENT`는 관찰 대상 중 하나이며 이 제품 의도와 구별한다.

표시 이름은 **Studio · 내 삶에 AI 더하기**다. 업무에 한정하지 않고 여행 준비,
취미, 공부 등 사용자가 자기 삶에서 선택한 작은 일을 실제 AI와 도구로 수행한다. 자신의 목적·맥락·판단이 결과에 어떻게 영향을 주는지 실제
산출물을 비교하여 이해하고, 그 과정에서 관찰된 7자산과 다음 학습 필요를 발견한다.
미션은 ‘AI가 일하는 세상에서, 판단하는 인간을 기른다.’이다.

체험은 Studio 프로그램이다. 웹 설문 점수, 작성된 예시 결과, 정해진 순서의
문제 풀이 완주는 이 Intent의 실현 증거가 아니다. 자유 대화가 어려운 사람에게는
한 번에 한 질문과 구체적인 시작 예시를 주되, 자기 목표를 말하면 이를 따른다.
완료를 위해 정해진 시나리오로 돌아오도록 강제하지 않는다.

## 접근 방식

기본안은 고객별 제한된 참여 코드다. 기존 서명 토큰, 프로필, roster,
session, 만료·폐기 정책을 재사용한다. 공용 bearer 토큰을 공개 페이지나
앱 설치본에 넣지 않는다. 모델 API 키는 기존 Worker에만 둔다.

고객 경로: Studio 설치/실행 → 기존 시작 화면에 코드 입력 → 체험 프로그램 확인
→ 자기 작업 폴더에서 실제 작업 → 산출물 비교와 관찰 결과 → 후속 커리큘럼.
웹의 역할은 설치·신청·사용 안내다. 자동 발급 페이지는 이후 동일한 Service
발급 경로에 연결할 수 있다. 별도 웹 AI 실행기는 첫 구현에 추가하지 않는다.

기존 발급 API의 `native_trial: true`로 개인 권한을 발급한다. roster·발급자 권한 검사는 유지하고, 첫 인증된 profile/context/chat 요청부터 개인별 1시간 창을 시작한다. 40회 요청 시도 한도와 동시 요청 1개 제한은 Service에서 적용하며 재발급으로 초기화하지 않는다. 실패한 요청도 시도 횟수에 포함한다. 이는 무제한 키나 금액 기준 비용 한도가 아니다. 전용 프로필은 `dashboard_hidden`이며 공개 자동 발급 화면은 별도 범위다.

## #764에서 파생한 행동 계약

상태: **요구사항 확정안 / 실행 검증은 별도**. #764는 안내·시작 예시·프롬프트를
바꾼 구현 후보이며 아래 전체 계약의 완료 증거가 아니다. 기존 NAT 식별자를 확장한다.

| 상황 | 요구 행동 | 기존 요구사항 / 실패 조건 |
|---|---|---|
| 다음 행동을 정할 정보가 이미 있다 | 그 행동을 시작한다. 이미 말한 목적·대상·제약을 재사용한다. 짧은 요청도 충분할 수 있고, 모든 필드를 채울 필요는 없다. | NAT-03 / 숙련도 설문, 결과물 카테고리 선택, 목적 재진술을 선행 조건으로 요구하면 실패 |
| 정보가 부족하다 | 다음 행동을 바꿀 가장 필요한 정보 하나만 묻는다. 답을 받은 뒤 충분하면 실행한다. | NAT-03 / 한 메시지 안에서 목적·대상·형식·예산을 모두 답하게 하거나 고정 여섯 단계로 되돌리면 실패 |
| 질문을 건너뛰거나 초안을 요청한다 | 되돌릴 수 있는 다음 행동에 필요한 가정을 밝히고 진행한다. 판단 불가능한 핵심 정보가 없으면 가능한 범위와 필요한 정보를 구분한다. | NAT-03·04 / 계속 진단을 강요하거나 없는 자료·실행 결과를 지어내면 실패 |
| ‘알아서 해줘’라고 위임한다 | 위임 범위를 대화에 반영하되 기존 Service 권한·호스트 승인·예산을 그대로 적용한다. | NAT-02·04·11 / 자연어·AI 이름·교수법·모델 선택으로 허용하지 않은 도구를 실행하면 실패 |
| AI 제안을 채택·수정·거절한다 | AI 제안과 사용자의 선택을 원본 역할·event ID로 구별한다. 기존 발화로 충분하면 이유 입력 폼을 추가하지 않는다. | NAT-05·06·08 / AI가 만든 목표를 독립적인 인간 판단으로 평가하거나 미관찰을 점수화하면 실패 |
| 마무리·내보내기·다른 작업을 원한다 | 산출물과 남은 한계를 보여준다. 짧은 성찰은 선택 사항이며 건너뛰어도 작업·종료가 가능하다. | NAT-07·09 / 성찰 응답이 파일 이용이나 종료의 필수 조건이면 실패 |

‘바로 실행’은 승인·인증·자료 부족을 무시한다는 뜻이 아니다. 사용자가 요청한 일을
완료하는 데 실제로 필요한 확인과, 교육 흐름을 완주시키기 위한 질문을 구별한다.
질문 수는 물음표 개수가 아니라 **사용자가 답해야 하는 독립 정보 항목**으로 판정한다.
도움받기·위임하기·질문 건너뛰기는 낮은 능력의 증거로 쓰지 않는다.

분기 정책과 예시는 Module의 역할이며 현재 구현 위치는 기존 trial profile/prompt다.
강사가 교수법을 바꾸는 Chalk UI는 E2의 후속 범위다. 강사 권한, 학습자별 상태 저장소,
새 관찰 스키마, 자동 원문 수집을 이 문서만으로 도입하지 않는다.

추적: [T04 확장과 연관 검증](../testing/studio-native-trial-validation.md#t04-product-intent-분기),
[E1–E7 구현 순서](../plan/learning-agent-experience-epics.md#product-intent에서-다음-구현으로).

## 체험 목적과 작업 화면 유지 (#758)

NAT-03은 사용자가 처음 밝힌 고민을 이후 과제 이름과 함께 유지한다. 위임 범위를
알고 싶다고 시작한 경우, 과제 종류를 알아내자마자 전체 제작으로 넘어가지 않고
AI가 도울 작은 범위와 사용자가 판단할 부분을 실제 작은 시도로 확인한다. 사용자가
이미 범위를 정했거나 완성본을 요청하면 그 선택을 따르며 필수 설문을 추가하지 않는다.

NAT-01/04의 시작 화면은 연결 전 안내다. 시작 후에는 같은 캔버스를 대화에 쓰고
결과물이 생기면 대화 옆에 보여준다. 홍보 화면을 작업 내내 띄우지 않는다. 기존
인증·기록·관찰 저장소를 재사용하며 연결 화면을 다시 열어도 대화 초안을 보존한다.

NAT-03의 작은 시도는 실제 초안이나 도구 결과가 있어야 한다. 역할을 구분한 뒤 “만들어볼게요”라고만 말하고 응답을 끝내는 것은 완료가 아니다. 결과를 만들 수 없는 경우에는 실제 오류·부족한 자료와 가능한 대안을 밝힌다.

검증: TUX-SP-03, TUX-CHAT-15/16, `e2e/tests/native-presentation.spec.ts`.
합성 대화의 의미 판정은 실제 원문을 검토해 기록하며 전송 성공으로 대체하지 않는다.

## 측정 설계

실제 API를 호출했다는 사실은 사용량의 증거다. 사람의 자산 성장을 뜻하지 않는다.
자동 관찰과 해석을 아래처럼 분리한다.

| 자산 | 관찰할 근거 | 충분하지 않은 근거 |
|---|---|---|
| TASTE | 대안 사이의 선택과 목적에 맞는 선택 이유 | 예쁜 결과 또는 ‘비교’ 단어 |
| INTENT | 사용자가 정한 목적·대상·완료 조건 | 코치가 대신 작성한 요구사항 |
| CONTEXT | 필요한 자료를 선택·제공하고 부족한 정보를 다룬 행동 | 입력 길이 |
| VERIFY | 검사 결과를 확인하고 오류를 수정·재검증한 행동 | AI의 ‘검증 완료’ 발화 |
| DELEGATE | 맡길 범위·승인 조건·사람이 남길 판단 | 승인 횟수 또는 자동 도구 호출 수 |
| ITERATE | 사용자 피드백 이유와 실제 변경·결과 비교 | 재시도 횟수 |
| OWNERSHIP | 결과 인수 판단, 한계 설명, 재열기·재사용 | 파일이 생성됐다는 사실만 |

평가 모델에는 역할이 분리된 기록을 데이터로 전달한다. 기록 속 명령으로 평가
규칙을 바꿀 수 없어야 한다. 반환한 event ID와 인용문은 서버/호스트에서 대조한다.
도구 실행 사실은 호스트 기록을 근거로 하되 이를 곧바로 사람의 역량으로 치환하지
않는다. 모델의 해석은 잠정 관찰로 표시하고 사람이 수정할 수 있게 한다.
오류·거절·근거 부족은 점수를 만들지 않는다. 현재 체험은 수치 점수나 1~5 레벨을 부여하지 않는다. 자동 완주·코칭·반복 횟수로 능력 향상을 주장하지 않는다.

기존 worker/src/lib/asset-scorer.ts는 정규식 기반이며 chat.ts는 AI 응답을 입력한다.
기존 max 누적 % 표시는 이 체험의 측정기로 채택하지 않는다. SDK의 역할별 기록을 별도 평가 API로 보내 잠정 관찰을 받는다. 연결이 지원되지 않거나 평가가 실패하면 그 상태를 명시한다.

## 레이어와 범위

App: 로컬 도구 실행 근거 수집과 결과 표시. Service: 기존 인증·실행, 평가 API,
사용량 정책. Module: 사용자 과제 탐색 코칭과 평가 루브릭. Chalk: 기존 운영자 발급 경로.
Lab: 안내와 커리큘럼 연결. 앱에 평가 임계값이나 직업별 수업 내용을 고정하지 않는다.
프로필은 기존 Profile 계약을 재사용한다. `hps-observation/1` 이벤트 계약과 App↔Service drift test, `hps-module/1` 관찰 루브릭을 사용한다. 소유권과 제거 경계는 [제품 등록부](../../products.yaml)를 따른다.

평가 전 사용자가 보낼 기록을 확인하고 동의한다. 확인한 event ID 집합이 달라지면 재확인이 필요하다. 원문 서버 보관·강사 열람은 켜지 않는다. 보관 정책 변경은 AUTONOMY-MANDATE의 별도 결정 사항이다.

## Validation → Intent 루프

프로그램은 실제 업무 선택, 초보자의 시작, 숙련자의 목표 변경, 무비판적 승인,
근거 검증, API 장애, 도구 거절, 코치에 의존한 개선, 새 과제의 독립 수행을 검증한다.
자동 테스트 통과와 고객의 AI 이해 향상은 구분한다. 고객이 ‘내 선택으로 달라진 점’과
‘아직 배워야 할 점’을 자기 말로 설명하지 못하면 코칭·비교 경험과 Intent를 수정한다.

인계 시점에는 전용 프로필과 기존 gate 계약만 있었다. 이후 구현 및 실제 API·Mac
실행 상태는 [실행 기록](../testing/studio-native-trial-results-2026-09-08.md)을 따른다.
공개 배포와 사람의 학습 효과는 별도 검증이며 로컬 성공으로 대신하지 않는다.
초기 인계의 API 자격증명 부족 상태는 이후 실제 API 검증으로 해소됐다. 사람의 학습 효과 파일럿 T25는 아직 NOT_RUN이다. 프로필 배포만으로 설치본 검증이나 사람 파일럿을 대신하지 않는다.

제거: 개인 체험 코드 발급을 중지하고 전용 프로필·관찰 API·App capability 표시를 각각 제거한다. 기존 사용자 파일과 기록은 보존한다. 사용량 감사에 필요한 D1 행을 삭제하거나 기존 코호트 정책을 변경하는 작업은 제거에 포함하지 않는다.
