# 강사 콘솔 디자인 요구사항

상태: 채택한 인수 기준 · 검토일 2026-09-07 · #732.
적용 대상: 신규 관리·공유 화면. 기존 화면의 충족 여부는 별도 검증한다.
목적: 강사가 수업 중 학생의 상태를 읽고 필요한 도움을 주며 학생은 공유 범위를 통제한다.
기존 모바일 기준에 더해 화면 구성과 상호작용의 합격 조건을 정의한다.

## Acceptance requirements

| ID | 디자인 요구사항 및 합격 기준 | 우선순위 |
|---|---|---|
| DES-01 | 첫 화면에 연결/수업 선택과 핵심 상태가 있다. 큰 홍보 문구·성과 카드 때문에 학생 목록 진입을 늦추지 않는다. | P0 |
| DES-02 | 본문은 16px 이상, 상시 라벨·상태는 14px 이상, 제목은 22~28px를 기본으로 한다. 200% 확대에서도 글자가 겹치거나 동작이 사라지지 않는다. | P0 |
| DES-03 | 375/390/768/1280/1440px에서 문서 가로 넘침이 없고 모바일은 목록→기록→피드백의 한 열로 읽힌다. 긴 URL·코드·한국어가 레이아웃을 밀어내지 않는다. | P0 |
| DES-04 | 정보 구조는 수업 연결, 학생 현황, 선택한 기록, 조치 순서다. 두 번 이내의 선택으로 공유 기록에 도달한다. | P0 |
| DES-05 | 상태는 글자로 구분한다. 색만으로 정상·오류·확인 불가를 표시하지 않고 데이터 시각·누락·명단 범위도 함께 보인다. | P0 |
| DES-06 | 모든 동작을 키보드로 수행하고 포커스가 보인다. 입력은 label과 연결하고 동작 대상은 최소 44×44px를 기본으로 한다. | P0 |
| DES-07 | 초기·로딩·빈 결과·부분 실패·401·403·409·만료·오프라인 상태를 구분한다. 실패한 갱신을 최신 정상 상태로 표시하지 않는다. | P0 |
| DES-08 | 저장 실패·충돌에서 입력이 유지된다. 동시 저장은 차단하거나 충돌을 보여주며 재연결 시 이전 사용자의 내용은 지운다. | P0 |
| DES-09 | 기본 운영 보드와 공유 원문을 시각적으로 분리한다. 공유 전 대상 강사·선택 내용·기한·철회 방법을 명시하며 동의를 미리 체크하지 않는다. | P0 |
| DES-10 | 수업 종료·권한 변경·삭제는 대상과 영향을 명확히 보여준다. 복구 가능한 동작은 복구 방법을 제공하고 조회 버튼이 쓰기를 일으키지 않는다. | P0 |
| DES-11 | 텍스트 대비 4.5:1, 큰 글자 3:1, 필수 컨트롤 경계·포커스 3:1을 기준으로 실제 색을 검사한다. 애니메이션 없이도 모든 정보와 기능이 유지된다. | P0 |
| DES-12 | 한국어 사용자 문구는 할 일·문제·다음 조치를 설명한다. 기술 오류 원문·토큰·스택을 UI에 노출하지 않으며 프롬프트 수를 능력 점수로 표현하지 않는다. | P0 |

숫자는 이 제품의 디자인 인수 기준이다. 출시 검증은 기기/브라우저·확대율·화면 폭·검사 날짜와
실제 관측을 기록한다. CSS 선언이나 단위 테스트 통과만으로 시각 검증 완료라고 표시하지 않는다.
합성 정상·긴 내용·오류·무신호 사례를 동일 화면에서 대조한다.


## 원격 운영 화면 적용 · 2026-09-18

[ADM 확장 PRD](classroom-admin.md#원격-수업-운영-확장-설계--2026-09-18)의 화면 상세를 아래 DES에 연결한다. 별도 대시보드 제품을 만들지 않고 기존 `/manage`를 확장한다. 구현·브라우저 인수는 NOT RUN이다.

- DES-01/04: 준비 확인 → 전체 학생 현황 → 선택 학생의 근거·조치 → 수업 마무리. 좌석/가명·입장·단계·수행·마지막 신호·문제·조치·기록을 한 행에서 읽는다. 현재 수업 명단을 항상 유지한다.
- DES-05/07/12: 빨간 글자는 확인된 차단 오류와 실패한 명령에만 사용하고 한글 사유·다음 조치를 함께 표시한다. 긴 대기/휴식과 오류, stale/unknown과 정상, 발급과 실제 활성화를 구분한다.
- DES-08/10: 단일/선택/전체의 대상 수·제외 사유·영향을 실행 전에 보여준다. 기본 reset은 한 명의 runtime만. queued/accepted/running/성공/실패/확인 불가와 마지막 갱신 시각을 유지한다. `모두 완료`는 대상별 결과가 모두 확정된 경우에만 쓴다.
- DES-09: 기본 좌석판은 메타데이터만. 원문 공유·수집은 별도 고지/권한 화면. 학생에게 누가 어떤 조치를 했는지 표시하고 로컬 Stop·거절/도움 요청을 제공한다.
- DES-02/03/06/11: 기존 5개 폭·200% 확대·키보드·대비 기준을 유지하며 색 없이도 동일한 판정이 가능해야 한다. 모바일은 열을 숨겨 정보가 사라지게 하지 않고 학생 카드 상세에 둔다.
- 종료 배치: 수집 중/미도착/불완전/초안/검수 대기/승인/전송/전달 확인·실패를 학생별로 분리한다. `수업 마무리` 버튼이 자동 발송을 포함하는지는 승인 범위와 함께 미리 표시한다. 수신자 수정이나 PDF 변경은 승인을 무효화한다.

### 디자인 시스템과 CTA 우선순위 (2026-09-18 보강)

근거: 금고의 `HypeProof_Studio_UIUX_Design_Philosophy.docx` §13·14(저장소 밖). 운영 패널에 적용하며 기존 DES-01~12를 대체하지 않는다.

- 색 토큰: 배경 `#151D19`, 패널 `#202C24`, 강조 `#D5F279`(주요 CTA·현재 단계), 주의 `#E6A373`(보류·확인 필요·가상/미확인 근거), 본문 `#F2F4E8`. 확인된 기술 장애의 빨간 글자는 별도 토큰으로 두고 대비를 실측한다. 본문·상태 4.5:1, 컨트롤 경계·포커스 3:1(DES-11)을 이 토큰 조합으로 다시 잰다.
- **2026-09-19 구조:** 학생 목록은 하나다. 회차 명단 목록에 기존 활동 상태를 합쳐 보이고, 기존 `학생 현황`에는 회차 명단 밖 학생만 남긴다. 선택한 학생의 상세는 넓은 화면에서 목록 오른쪽 고정 패널, 1080px 이하·200% 확대·모바일에서 drawer다(Enter로 열기, Esc·배경으로 닫기, 포커스는 연 행으로 복귀). 30좌석 목록은 자체 영역에서 스크롤한다. 주요 CTA는 **화면 기준** 하나다 — 상세가 열려 있으면 그 행동이 주요 CTA이고 목록의 CTA는 일반 버튼이 된다.
- 한 화면(패널)의 주요 CTA는 원칙적으로 하나다. 기본 상태의 주요 CTA는 `준비 확인`/`도움 필요한 학생`이고, 학생 상세에서 기술 장애가 확인되면 **복구 조치가 주요 CTA**가 되며 `수업 마무리`·코칭·코드 발급은 보조로 내린다. 기술 장애가 없으면 상세의 주요 CTA는 `질문 보내기`다.
- 강사 개입 문구: `답변하기` 대신 `질문 보내기`, `수정해주기` 대신 `확인할 지점 표시`, `평가 완료` 대신 `근거 확인 / 추가 관찰 필요`.
- 상태는 색만으로 표현하지 않는다(글자 + 기호). 주의색은 근거 부족·느린 진행을 **실패로 읽히게 쓰지 않는다**: 해당 문구는 중립 색과 `아직 충분히 보지 못함`/`확인 불가`를 쓴다.
- 인원 집계(도움 필요·연결 미확인·준비 완료)는 운영 수치로만 표기한다. 학생별 점수·순위·채팅량·토큰량·체류시간·AI 의존도 추정치를 능력 지표로 표시하지 않는다.

검증: AT-15~39, 기존 DT-01~06과 DT-07. 실제 UI와 비용·전달 상태 없이 성공 화면만 만드는 목업을 기능 완료로 보고하지 않는다.

### 강사 페르소나 UI 1차 정리 · 2026-09-22 (사용자 검토 전 시안 · 인수 아님)

대상 사용자: PC 수업을 혼자 운영하는 강사([1인 강사 운영 의도](../PRODUCT-INTENT.md#one-instructor-classroom-intent)).
강의 도중 몇 초 안에 “누가 어느 단계에서 막혔고, 무엇을 할 수 있고, 실제로 적용됐는가”를 읽는 것이 목표다.
20~30석은 가독성 시험용 합성 규모이며 고객 정원이 아니다. 근거 문서는 위 절과 같은 docx(concept v1)의
§13·14 원칙(수업이 전면·측정은 후면, 근거·도움 중심, 상태는 색+문구, 주요 CTA 하나)만 적용하고, 문서 속 예시를
전역 규칙으로 올리지 않는다. 기능·권한·API·Service 판정은 바꾸지 않았다 — 화면 배치·문구·스타일만이다.

- **공통 동선(DES-01/04):** `/authoring`·`/issuer`·`/budgets`·`/console`·`/manage` 상단에 같은 3단계 막대
  `1 수업 준비(강의 작성·학생 초대·토큰·AI 예산) → 2 수업 진행(수업 열기·종료·운영 보드) → 3 마무리(도움·결과물·기록 회수·보고서)`.
  현재 화면은 `aria-current`로 표시하고, 좁은 화면에서는 줄바꿈 대신 막대 안에서 가로로 넘긴다(문서 가로 넘침 없음).
  기존 경로를 그대로 링크하며 새 경로·인증을 만들지 않는다. 학생용 `/sharing`은 강사 도구에서 빼고 공유 패널 안내문에 링크한다.
- **연결은 접는다(DES-01):** `/manage`에서 Board가 이 토큰으로 응답하면 입력 폼을 한 줄 요약(코호트·학생 접두어·
  “토큰은 이 창의 메모리에만”)으로 접고 `지금 갱신`·`접속 설정`·`연결 해제`만 남긴다. 401이면 폼을 다시 편다.
  토큰 보관 범위는 바꾸지 않았다(메모리만, 표시·저장 없음).
- **학생 목록이 주 영역:** 패널 제목을 `이번 수업 학생`으로 바꾸고, 첫 줄에 행 표식과 같은 기준의 운영 집계
  (`✕ 기술 장애 확인`·`! 주의`·`✋ 도움 요청`·`? 확인 불가`·`✓ 정상`·명단 수 — 학생 평가 아님)를 둔다. 수업·강의·조회 시각과
  `새 AI 실행` 제어는 한 줄로 묶었다. 작성기(공지·자료·프롬프트·수업 설정)는 조치 버튼 줄의 점선 항목으로 접어 두고,
  열면 그 아래에서 쓰기 → 확인이 위에서 아래로 이어진다. 1280×720에서 첫 학생 행이 약 434px(수정 전 U3 관측 약 705px).
- **좌석 행:** 좌석 ID를 크게, 학생 ID는 작게. 상태 표식은 기호+문구(`✕ 차단됨`·`! 주의`·`? 확인 불가`·`✓ 정상`)와 행 왼쪽
  색 띠로 이중 표기하고, 정상 행에는 오류색을 쓰지 않는다. 원인 문장이 있으면 행의 첫 줄 전체 폭으로 올린다.
  나머지 사실(입장·단계·수행·신호·기록·근거)은 두 열(상세가 열려 있거나 좁으면 한 열)이다. 질문·토큰 수로 순위를 만들지 않는다.
- **상세 패널 순서:** `원인과 조치 결과`(지금 보이는 원인 → 먼저 할 조치 → 마지막 조치 → 조치 뒤 검증) → 조치 버튼 →
  조치 결과 → 학습 근거·단계 확인 → `연결·보고 기록 (현장 확인용)`(발급 ID·요청 ID 등 기술 값). ‘진단 완료=해결’로 바꾸지 않는
  Service의 판정 문구는 그대로다.
- **결과 목록:** 배포·선택 회수·수업 마무리 결과를 학생당 한 줄 목록으로 통일하고 기호를 붙인다 — `✓` 확정·반영, `✕` 실패
  (배포 `failed`, 수업 설정 `attempt_failed`, 회수 `refused` — DES의 ‘실패한 명령은 빨강’), `!` 다시 볼 대상, `…` 진행 중·접수·제외.
- **다른 화면:** `/console`·`/issuer`의 파란 강조를 브랜드 토큰(배경 `#151D19`, 강조 `#D5F279`)으로 바꾸고 14px 미만 라벨을 올렸다.
  `/issuer` 설명을 강사 용어로 바꾸고 “발급은 연결 완료가 아님”을 적었다. `/authoring`의 밝은 작성 화면은 유지했다.

남은 결정·후보(사용자 피드백 대기): ~~연결 직후 `준비 확인`을 자동으로 할지~~(2차에서 조작 결함으로 처리 — 아래), 행 정렬(도움 필요 우선)과 필터, 상세의 기술 값을
기본 접힘으로 할지, `/authoring`·`/console`·`/issuer` 본문 재설계 범위. 실행 기록과 캡처는
[시험 문서](../testing/classroom-admin.md#instructor-ui-pass-run-20260922).

#### 2차 보완 · 2026-09-22 — 강사 조작 결함 4건 (시각 취향·디자인 승인 아님)

출처: 1차 화면 독립 검토(Codex, `remote-classroom-evidence/management-20260921/instructor-ui-review/codex/review.json`)에서
**객관적으로 재현된** 조작 결함만. 새 디자인 방향이나 사용자 승인이 아니다. Service·SDK·토큰 발급·DB는 바꾸지 않았다.

1. **연결 = 명단 조회 시작.** 상단이 ‘연결됨’인데 학생 영역이 ‘연결하지 않았습니다’로 남던 불일치를 없앴다. Board가 이 토큰으로 응답하면
   같은 토큰·같은 generation으로 이번 수업 명단을 바로 읽고, 응답 전까지 “강사 연결 확인됨 · 불러오는 중 (연결 확인은 학생 상태가 아닙니다)”라고 쓴다.
   `준비 확인` 버튼은 `현황 새로 확인`(수동 갱신)이 됐다. 인증 거부·운영 권한 없음·열린 수업 없음·조회 실패는 각각 그 사유로 목록과 집계를 함께 비운다(이전 현황을 남기지 않음).
   연결 성공을 전원 정상으로 세지 않는다 — 무신호·미연결은 계속 `? 확인 불가`.
2. **학습 도움 요청 ≠ 기술 문제.** ‘도움 필요한 학생 선택’(실제로는 attention `blocked/caution`)을 둘로 나눴다:
   `도움 요청 학생 선택 (n)` — 이번 수업(session)에서 학생이 직접 보낸 도움 요청이 `접수`/`검토 중`이고 만료 전인 학생,
   `기술 문제 좌석 선택 (장애 n · 주의 n)` — 기존 attention 기준. 집계 칩 `✋ 도움 요청`도 같은 정의(학생 수)를 쓴다.
   판정은 공유 **metadata**(kind·status·session_id·expires_at)만 쓰고 내용은 읽지 않는다. `답변 완료 · 학생 확인 대기`·`학생 해결 확인`·
   철회(Service가 삭제)·만료·다른 수업의 요청은 현재 도움 목록·집계·선택에서 빠진다(다른 수업의 기록은 공유 기록 목록에 ‘다른 수업의 기록’으로 남는다).
   도움 요청은 행을 빨갛게 만들지 않는다. 새 API·저장소 없음.
   통합 보완(2026-09-22, Codex 검토 P2): 공유 기록 조회가 **실패했거나 아직 없으면 ‘도움 요청 없음’이 아니라 ‘확인 불가’**다 — 도움 요청 영역·집계 칩(`도움 요청 확인 불가`)·
   좌석 카드·`도움 요청 학생 선택 (확인 불가)`(비활성)가 같은 말을 한다. 응답 행 수가 Service 한도(`limit`)에 닿으면 오래된 요청이 잘렸을 수 있어 수를 하한(`n 이상`)으로 쓴다.
   조회 실패는 명단·선택·열린 공유 기록과 쓰던 피드백을 지우지 않으며, 다음 성공 조회(10초 갱신)가 복구한다.
   통합 후속(2026-09-22, Codex F2): 위 ‘한도 도달=하한’은 Service가 강사 범위 필터 **전** 100행에서 잘라 틀릴 수 있었다(범위 밖 새 행 100개 뒤의 허용된 요청이 0건으로 보임).
   이제 도움 요청은 공유 목록과 **따로** 이번 수업·도움 요청만(`session_id`·`kind=help`) 읽는다. 완결성은 Service의 `has_more:false`로만 판단하고,
   일부만 읽힌 경우 응답할 요청 수는 Service `counts.open`(정확한 값)으로, 학생 수는 하한(`n명 이상`)으로 쓰며 `더 오래된 도움 요청 불러오기`(최대 10쪽)를 준다.
   다음 쪽 조회가 실패하면 전체를 ‘확인 불가’로 되돌린다. 집계가 없는(이전 Service) 불완전 응답에서 보이는 요청이 0건이면 ‘요청 없음’이라고 하지 않고
   “불러온 범위에는 … 더 오래된 요청은 확인하지 못했습니다 (요청 없음이 아님)”과 `다시 확인`을 준다. 공유 기록 목록도 같은 계약(`더 오래된 기록 불러오기`)이고,
   열린 공유 기록은 **완결된** 목록에 없을 때만 닫는다(한 쪽에 없다는 것은 철회가 아니다 — 철회·만료·권한 없음은 저장 시 Service 404가 막는다).
   통합 후속 2(2026-09-22, Codex F2b): ‘최대 10쪽’은 그 뒤의 허용된 요청을 영구히 못 닿게 했다(새 답변함 1000건 뒤의 오래된 접수 1건 → ‘1건 (이 화면에 0건)’과 `다시 확인`만).
   이제 ① 도움 요청은 Service에 `status=open`으로 **응답 대기 요청만** 요청한다 — 답변함은 `counts`로만 세고 쪽으로 넘기지 않는다. ② 두 목록 모두 **커서 창**이다:
   시작 커서(없으면 최신) + 최대 3쪽. 10초 갱신은 창만 다시 읽는다(앞 쪽 전부를 다시 읽지 않음). `더 오래된 … 불러오기`는 창을 3쪽까지 늘리고, 그다음엔 창을 Service의
   다음 커서로 옮긴다 — 깊이와 무관하게 모든 허용 기록에 닿는다. 옮긴 창에는 `최신 요청부터 보기`/`최신 기록부터 보기`가 붙고 “더 오래된 … n건을 보고 있습니다”라고 쓴다.
   최신에서 시작하지 않는 창은 완결이 아니므로 열린 공유 기록을 닫지 않는다. 커서는 `created_at:id` 키셋이라 새 행·철회에도 창의 자리가 유지되고, 쪽 조회가 실패해도
   창은 유지된 채 ‘확인 불가’가 되며 다음 성공 조회가 같은 창을 되살린다. `status`를 모르는 이전 Service는 필터를 무시하고, 화면은 전처럼 직접 거른다.
3. **첫 조치 = Service의 `recommended.action`.** 이전에는 `issuer`·`pairing`·`collection`·`none_shared_incident`처럼 명령 원장 밖의 조치를
   화면이 몰라 장애 좌석에 ‘진단 다시 실행’을 주요 버튼으로 붙였다. 이제 그 조치가 화면의 유일한 주요 CTA다 —
   토큰 거부: 재발급 링크(고정 강의 수업은 `/authoring` 수업 참여 코드 발급, 강의 버전 유지 — U4 `9b0c643`의 링크 규칙과 같음; 새 탭),
   미연결: `기기 연결` 묶음을 맨 위로 올리고 연결 코드 발급, 공통 장애(incident): 개별 PC 주요 조치 없음 + “이 좌석에서 먼저 할 개별 조치는 없습니다”,
   기록 전송 실패: 이 학생을 선택해 ‘기록 회수’로 이동. 권장 문구·다음 조치 문구의 재발급 화면 이름도 같은 규칙으로 바꾼다. 공통 원인 안내는 복구 묶음 맨 위로 옮겼다.
4. **도움 응대는 ‘2 수업 진행’.** 5개 화면 공통 동선: `2 수업 진행 = 수업 열기·종료 · 운영 보드 · 도움 요청 응대`, `3 마무리 = 결과물·공유 기록 · 기록 회수·보고서`.
   `/manage` 안에서는 같은 화면 앵커(`#ops-help-title`, 운영 보드는 `#ops-title`)라 열린 상세·작성 중인 질문·선택·공유 피드백 초안을 잃지 않는다.
   학생 목록 위 `도움 요청 응대`에 응답할 요청이 한 줄씩(좌석·학생·상태·시각, `요청 열기`·`좌석 상세`) 보인다. 휴대폰에서는 상세 서랍을 닫아야
   동선에 닿으므로 보내지 않은 질문은 화면 메모리에 남기고, 동선 막대는 현재 화면 위치에서 시작한다.
   통합 보완(2026-09-22, Codex 검토 P2): 보내지 않은 질문은 **수업 회차(class run) + 학생 + 좌석**에 묶인다. 상세를 닫았다 열거나 무관한 좌석의 명단 변경에는 유지되고,
   같은 좌석이 다른 학생·다른 수업으로 바뀌면 상세의 조치 영역을 다시 그려 빈 질문으로 시작하고 “쓰던 질문을 이 학생에게 옮기지 않았습니다”라고 알린다.
   보내기 직전에도 좌석의 현재 학생·수업을 다시 대조해 다르면 보내지 않는다.
   통합 후속(2026-09-22, Codex F1): 조치 영역은 식별자만이 아니라 **연결 상태·연결 세대, 이 토큰의 허용·활성 조치와 플래그, 강의 단계, Service의 원인·첫 조치**가
   바뀌면 상세를 다시 열지 않아도 그 자리에서 다시 그린다(“기기 연결·조치 권한·원인이 바뀌어 지금 할 수 있는 조치를 다시 표시했습니다”). 신호 시각 같은 심장박동에는
   다시 그리지 않는다. 같은 식별자의 질문·확인 지점 입력과 포커스는 유지하고, 다른 식별자로 초안을 옮기지 않는다. 모든 보내기(복구·질문·확인 지점)는 직전에
   같은 학생·수업, 연결됨, 이 토큰의 허용 조치를 다시 대조해 하나라도 다르면 보내지 않는다(연결 해제 뒤 명령 없음). 운영 현황 조회가 실패하면 열린 상세의 조치를 막는다.
   통합 후속 2(2026-09-22, Codex F1b): 보내지 않은 **확인 지점 메모·단계**도 질문과 같은 경계를 따른다 — 연결 해제·다른 강사·같은 강사의 재연결(모두 새 인증)에서 비우고,
   코호트·수업 회차·좌석의 학생이 바뀌면 옮기지 않는다. 같은 연결 안에서 같은 식별자의 실시간 재그리기에만 유지된다.

검증: `e2e/classroom/ops-help.mjs`(신규) 및 갱신된 `ops.mjs`·`ops-roster.mjs` — [실행 기록](../testing/classroom-admin.md#instructor-ui-pass2-run-20260922), U4 통합본 [실행 기록](../testing/classroom-admin.md#instructor-ui-integration-run-20260922), 통합 후속 [실행 기록](../testing/classroom-admin.md#instructor-ui-integration-followup-run-20260922), 통합 후속 2 [실행 기록](../testing/classroom-admin.md#instructor-ui-integration-followup2-run-20260922).

| **선택 도구** — 선택≠발송, 실제 대상 수, 맥락별 주요 행동, 보조 행동 묶음 | 1줄: 현재 선택(대상 수·연결 여부·좌석 목록) + 도움 요청/기술 문제로 고르기·선택 해제·‘다른 조건으로 선택’(전체·연결됨·미연결). 2줄: ‘선택한 학생에게’ 좌석 진단·기록 회수·보내기·작성. **주요 버튼 하나**는 선택 없음 → 문제 좌석 고르기, 저장된 공지 있음 → 보내기, 기술 문제 좌석 포함 → 진단, 그 밖 → 회수. 주요 버튼도 먼저 확인 화면만 연다. 확인 패널이 열려 있으면 목록의 주요 버튼은 물러난다. 동의·담당·수업·권한·오래된 대상 검사와 기존 확인 단계는 그대로다. 임의 셸·원격 데스크톱 조작은 추가하지 않았다 | ops-g1 ③, ops-selection, ops-distribution |
| **결과 카드** — 첫 줄 = 조치 + 확정/미확인/진행 중 + 다음 행동 | 제목 줄: “진단 다시 실행 — 결과 확정 1 · 미확인 0 · 진행 중 1 / 2명 · 해결 확인 0 · 다음: …”. 그 아래 흐름별 단계 수(기존), 학생별 짧은 상태(서버 검증·범위·잘린 결과물·세션 끝 확인 불가·앱 업데이트 필요 등). 세션 범위·무결성·범위 사유는 ‘세부 근거 펼치기’. 조치마다 카드가 따로이고 지금 선택이 이전 결과를 다시 겨누지 않는다(“보낼 때의 대상 기준”). 접수·수신·준비는 적용·해결·완료가 아니다. 실패만 다시 고르기는 선택만 한다. F1~F3·철회/승인 경합 수정은 서버 쪽이라 그대로다 | ops-results, ops-g1 ⑤ |
| **마무리 단계** | ‘수업 마무리 단계’: 1 기록 회수 → 2 보고서 초안 → 3 검수 → 4 발송. 각 칸은 이 화면이 서버에서 받은 사실만 쓴다(검증 수/명단, 초안 작업·검수 대기·승인 수, 발송 승인·요청). 꺼진 단계는 “사용할 수 없음”과 이유. 아직 없는 경로(재시작 전 세션을 담은 `/3` 회수를 보고서 입력으로 쓰기, 반복 패턴 본문, 카카오·문자·QR, PDF 첨부)는 완료로 표시하지 않고 명시한다. 목록에서 고른 학생의 회수는 보고서로 이어지지 않는다 | ops-g1 ⑥ |
| **다른 강사 화면 유지** | `/authoring`·`/issuer`·`/budgets`·`/console` 링크, 도움 요청 목록, 명단·관측 설정(검토된 단계 입력), 예산 링크, 조치별 이력은 그대로 닿는다. 다른 화면의 본문은 바꾸지 않았다(이번 캡처는 `/manage`만 대표한다) | ops-help, ops-roster |

교실 배치와 맞추고, 필터 한 번으로 해당 학생만 본다. 사용자 시각 인수·실제 강사 운영 관측은 아직 없다.
