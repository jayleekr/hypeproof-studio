# 리허설 진입 — 안 되면 어떻게 되나

상태: 제안. 구현·운영 정책으로 아직 채택하지 않음. 날짜: 2026-09-19 ·
[#1131](https://github.com/jayleekr/hypeproof-studio/issues/1131) ·
[#1132](https://github.com/jayleekr/hypeproof-studio/issues/1132).

계약은 `ARC-03`([요구사항](../requirements/chalk-authoring.md))이다. 강사가 브라우저에서
**리허설 링크를 한 번 누르면** 앱이 그 수업을 학생 조건으로 연다. 링크는 **일회용 교환권 하나만**
나르고 좌표·자격증명을 URL 에 싣지 않는다.

이 문서는 **그게 안 될 때**를 강사가 겪는 순서로 늘어놓는다. 데모에서 나올 질문은
"되나요"가 아니라 "안 되면 어떻게 되나요"이기 때문이다.

표기: ✅ 정해졌고 구현됨 · 🟡 정해졌으나 미구현 · ⬜ **아직 안 정했다** · ❓ 정했지만 **실기기 미확인**

**출처 구분**: 🅡 는 **Router 결정 · 근거 포함 · Jay 검토 전**이다. 표시 없는 ✅/🟡 은
기존 요구사항·코드에서 이미 정해져 있던 것이다. **위클리에서 뒤집힐 때 어디까지 뒤집히는지
알려면 누가 정했는지가 남아 있어야 한다.**

> ⬜ 를 채우지 않고 남겨 둔다. **비워 두는 것이 지어내는 것보다 낫다.**

## 0. 한눈에

```
강사가 Chalk 에서 [Studio에서 리허설] 을 누른다
      │
      │  (스킴을 바로 쏘지 않는다 — 리허설 카드를 띄운다) 🅡
      ├─ 앱이 설치돼 있지 않다 ──────────────► 🅡 카드가 그대로 남아 받는 곳을 말한다
      ├─ 앱이 구버전이다 ────────────────────► ✅ "앱을 업데이트해 주세요"
      ├─ 앱이 꺼져 있다 ─────────────────────► ❓ 뜨면서 받는지 미확인
      │
      ▼ 앱이 링크를 받는다
      ├─ 5분 안에 다시 눌렀다 ───────────────► 🅡 **그냥 열린다** (실패를 겪지 않는다)
      ├─ 교환권을 이미 썼다 (5분 뒤) ────────► ✅ "이미 사용했습니다 · 다시 받으세요"
      ├─ 교환권이 만료됐다 ──────────────────► ✅ "유효 시간이 지났습니다 · 새 링크"
      ├─ 그 사이 수업 내용이 바뀌었다 ───────► ✅ "내용이 바뀌었습니다 · 새 링크"
      ├─ 네트워크가 끊겼다 ──────────────────► ✅ "연결을 확인하고 다시"
      ├─ 링크에 좌표·자격증명이 실려 있다 ───► ✅ 거부 (계약 위반 링크)
      │
      ▼ 학생 조건 자격을 받았다
      ├─ 리허설 좌석 ────────────────────────► 🅡 교환권 하나 = 좌석 하나 (부딪힐 게 없다)
      ├─ 강사가 이미 다른 수업에 연결돼 있다 ► ⬜ 안 정함
      └─ 수업이 열린다 ──────────────────────► ✅ 기존 참여 경로 그대로
```

**확인 다이얼로그는 붙지 않는다** — 양성 대조를 세우고 실측했다. 한계는 §4.1 에 함께 적었다.

## 1. 앱에 닿기 전 — 링크를 누른 직후

| 상황 | 화면에 뜨는 말 | 강사가 다음에 하는 행동 | 상태 |
|---|---|---|---|
| **앱이 설치돼 있지 않다** | 리허설 카드가 그대로 남아 있다: `[Studio 에서 열기]` 밑에 "안 열리면 Studio 가 없거나 옛 버전입니다" + **받는 곳** | 카드가 가리키는 곳에서 Studio 를 받고 **같은 카드의 버튼을 다시 누른다** | 🅡 |
| **앱이 구버전이라 링크를 모른다** | "이 앱 버전은 아직 리허설 링크를 지원하지 않습니다. 앱을 최신 버전으로 업데이트한 뒤 다시 시도해 주세요." | 앱을 업데이트하고 **같은 링크를 다시 누른다** | ✅ |
| **앱이 꺼져 있다** | (앱이 뜨고 그 수업이 열린다) | 없음 | ❓ |

### 1.1 스킴을 바로 쏘지 않는다 — 리허설 카드를 띄운다 🅡

**계약**: 저작 화면이 리허설 링크를 만들면 **새 창으로 스킴을 던지지 않는다.** 대신
**리허설 카드**를 띄운다. 카드에는 `[Studio 에서 열기]` 버튼과 그 밑에
*"안 열리면 Studio 가 없거나 옛 버전입니다"* + **받는 곳**이 함께 있다.

**근거**: 등록되지 않은 커스텀 스킴은 **조용히 아무 일도 안 한다.** 그게 우리가 만들 수
있는 최악의 실패다 — 강사는 "눌렀는데 안 되네" 만 겪고 **무엇이 잘못됐는지도, 다음에 뭘
할지도 모른다.** 확정 관문에서 이미 *"못 하는 이유와 하면 어떻게 되는지를 같이 말한다"* 를
원칙으로 세웠다. **진입점이 그 원칙을 어기면 안 된다.**

부수 효과: **브라우저가 확인 대화상자를 띄우는지 여부에 설계가 덜 매달린다.** 눌러서
아무 일도 안 나도 카드가 그대로 남아 다음 행동을 말해 준다.

**이건 저작 화면(Chalk) 쪽 일이다.** 여기서는 계약으로만 적는다 — 구현은 `#1128` 스택이
자기 차례에 가져간다.

### 1.2 구버전이 실제로 생긴다

앱 릴리즈와 Service 배포 주기가 다르므로 **Service 에는 교환 경로가 있는데 앱에는 없는
기간이 생긴다.** 그 상태에서 404 를 "링크가 틀렸다"로 읽으면 강사는 **멀쩡한 링크를 버리고
새로 만들러 간다.** 그래서 앱은 `404` + 빈 오류 본문을 **"앱이 아직 지원 안 함"** 으로 읽고,
`404` + `not_found` 를 **"교환권이 없음"** 으로 읽어 둘을 갈랐다
(`rehearsalEntryHelpers.ts` `classifyRedeemFailure`).

## 2. 앱이 링크를 받은 뒤 — 교환 단계

판정은 전부 Service 가 한다. 앱은 받아서 연다.

| 상황 | 화면에 뜨는 말 | 강사가 다음에 하는 행동 | 상태 |
|---|---|---|---|
| **5분 안에 같은 링크를 다시 눌렀다** | (아무 실패도 안 뜬다 — 그냥 열린다) | 없음 | 🅡 |
| **이미 쓴 링크** (5분이 지난 뒤) | "이 리허설 링크는 이미 사용했습니다. 링크는 한 번만 열 수 있습니다. 수업 작성 화면에서 리허설 링크를 다시 받아 주세요." | Chalk 로 돌아가 링크를 다시 받는다 | ✅ |
| **만료** | "리허설 링크의 유효 시간이 지났습니다. 수업 작성 화면에서 새 링크를 받아 주세요." | 같음 | ✅ |
| **그 사이 수업이 바뀌었다** | "링크를 받은 뒤 수업 내용이 바뀌었습니다. 바뀐 내용으로 리허설하려면 수업 작성 화면에서 새 링크를 받아 주세요." | 같음 | ✅ |
| **교환권을 확인할 수 없다** | "이 리허설 링크를 확인할 수 없습니다. 수업 작성 화면에서 새 링크를 받아 주세요." | 같음 | ✅ |
| **네트워크가 끊겼다** | "리허설 링크를 확인하지 못했습니다. 연결 상태를 확인하고 다시 시도해 주세요." | 연결을 고치고 **같은 링크를 다시 누른다** | ✅ |
| **링크에 좌표·자격증명이 실려 있다** | "이 링크는 열 수 없습니다. 수업 작성 화면에서 리허설 링크를 다시 받아 주세요." | 같음 | ✅ |
| **Service 가 알 수 없는 오류** | "리허설을 시작하지 못했습니다. 잠시 후 다시 시도하고, 계속되면 운영 담당자에게 알려 주세요." | 재시도 후 문의 | ✅ |

### 2.1 교환은 일회용이되 **멱등**이다 🅡

**계약**: 교환권을 받으면 서버는 자격을 발급하고 **그 결과를 교환권에 붙여 둔다.**
같은 교환권이 **짧은 창(권장 5분) 안에** 다시 오면 **새로 발급하지 않고 붙여 둔 그 자격을
그대로 돌려준다.** 창이 지나면 만료다.

**근거**: 일회용의 목적은 **링크가 새 나갔을 때 남이 못 쓰게** 하는 것이지 **주인이 재시도
못 하게** 하는 게 아니다. 일회용을 글자 그대로 구현하면 **네트워크가 한 번 튄 강사는 링크를
영영 못 쓴다 — 수업 직전에.** 멱등 재발급은 앞의 목적을 지키면서 뒤의 문제를 푼다. 노출
창은 5분으로 제한된다.

**이것이 두 번째 클릭의 문구를 바꾼다.** 5분 안이면 강사는 **실패를 아예 겪지 않는다**(그냥
열린다). 5분 뒤에야 *"이미 사용됐습니다"* 다. 앞선 구분에 **"조용히 성공"** 한 칸이 앞에 붙는다.

두 번째 클릭은 어차피 실수가 아니다 — 창을 잘못 닫았거나, 탭이 남아 있거나, 되던 것을 다시
해 보는 것이다. 그래서 5분 뒤 문구도 `already_used` 를 일반 오류로 뭉개지 않고 **"한 번만 열
수 있습니다"** 라고 성질을 먼저 말한 뒤 다음 행동을 붙였다.

### 2.2 네트워크 실패는 교환권을 태우지 않는다

서버에 **닿지 못한** 경우 교환권은 소모되지 않는다 — 같은 링크가 다시 통한다. 앱은 이미
그렇게 읽는다("서버에 닿지도 못했다 — 교환권은 용의자가 아니다").

**요청이 서버에 닿았는데 응답만 유실된 경우를 앱은 구분할 수 없다.** §2.1 의 멱등 창이
정확히 이 경우를 덮는다 — 앱은 그냥 다시 내면 되고, 서버가 같은 자격을 돌려준다.
**앱 쪽에는 이 때문에 고칠 코드가 없다**: 재시도가 `200` + 자격으로 돌아오는 것은 첫 교환과
같은 경로다(`redeemRehearsalTicket`).
⬜ 창의 정확한 길이와 붙여 둔 자격의 저장 위치·정리 방식은 교환 엔드포인트 구현에서 정한다.

## 3. 자격을 받은 뒤 — 수업이 열리는 단계

| 상황 | 화면에 뜨는 말 | 강사가 다음에 하는 행동 | 상태 |
|---|---|---|---|
| **정상** | 시작 화면에 그 수업이 뜬다(제목·버전·목표·단계) | 학생처럼 해 본다 | ✅ |
| **리허설 좌석** | (좌석이 없어서 막히는 경우가 없다 — 교환권 하나가 좌석 하나다) | 없음 | 🅡 |
| **강사가 이미 다른 수업에 연결돼 있다** | ⬜ | ⬜ | ⬜ |
| **열린 세션이 없다** | (아무 말도 안 뜬다 — 리허설은 세션을 요구하지 않는다) | 없음 | 🟡 |
| **창이 여러 개 열려 있다** | ❓ 어느 창이 받는지 확인 안 함 | ❓ | ❓ |

### 3.1 좌석은 교환권 단위로 낸다 🅡

**계약**: **교환권 하나 = 리허설 좌석 하나.** 공유 좌석을 미리 만들어 두지 않는다.
교환권의 수명이 곧 좌석의 수명이다.

**근거**: 그러면 *"두 강사가 같은 코호트를 동시에 리허설하면 부딪히는가"* 가 **질문 자체로
사라진다** — 부딪힐 공유 자원이 없다. 이름·생성 시점·재사용을 따로 정할 필요도 없어진다.
참여 코드 발급이 요구하는 **로스터 게이트를 뚫지 않으면서** 리허설이 운영 명단을 건드리지
않는 것도 같이 해결된다 (`worker/src/routes/authoring.ts`).

**리허설은 운영 보드(`/board`)에 보이지 않는다.** 보드는 **실제 학습자가 어디까지 갔는지를
강사가 보는 곳**이고, 거기에 리허설이 섞이면 **보드가 거짓말을 한다.**

**보이지 않게 하는 것과 기록에 안 남기는 것은 다르다.** 좌석 기록 자체에는 **리허설임이
남아야** 나중에 "이게 진짜였나" 를 물을 수 있다. 몇 달 뒤 운영 데이터를 보는 사람이 그것을
실제 학생으로 세지 않아야 한다.

### 3.2 이미 다른 수업에 연결된 상태

앱은 지금 새 연결을 **미리보기**로 받고 기존 연결을 workspace 준비가 성공할 때까지
유지한다(`startPage.ts`). 리허설 링크도 같은 경로를 타므로 **강사는 어떤 수업이
열리는지 보고 나서 진행한다.**

⬜ 안 정한 것: 강사가 **수업 중에** 실수로 리허설 링크를 누르면 어떻게 되는가.
진행 중인 수업을 건드리지 않아야 한다는 것은 분명하지만, 그것을 **어떻게 보이게 할지**
정하지 않았다.

### 3.3 열린 세션을 요구하지 않는다

리허설은 **수업을 열기 전에** 하는 일이다. 열린 세션을 요구하면 순서가 뒤집힌다
(열어야 리허설하고, 리허설해야 여는데). 학생 조건은 **권한과 환경**을 뜻하지
세션이 열려 있느냐가 아니다 — `RUN-01` 에 명시했다.

## 4. 확인 다이얼로그 — 붙지 않는다 (✅ 실측)

출하된 앱(v0.1.56) 번들 `out/main.js` 를 읽어 확인했다:

1. 프로토콜 URL 의 경고 모달은 `getWindowOpenableFromProtocolUrl` 이 값을 돌려줄 때만 닿는다.
2. 그 함수는 authority 가 `file` 또는 `vscode-remote` 일 때만 값을 낸다.
3. `shouldBlockOpenable` 안에도 **같은 조건이 한 번 더** 있다.

우리 링크의 authority 는 확장 id(`hypeproof.hypeproof-chat`)이므로 **두 겹이 독립적으로
배제한다.** 따라서 `security.promptForLocalFileProtocolHandling` 을 끌 이유도 없다 —
그 설정을 끄는 것은 아무 웹페이지나 로컬 파일을 열 수 있게 만드는 일이다.

### 4.1 실측 — 양성 대조를 먼저 세우고 쟀다 ✅

**계측기**: 메인 프로세스의 `dialog.showMessageBox` 를 가로채 호출을 센다
(Playwright `_electron` 으로 앱을 띄우고 `app.evaluate()` 로 패치).
경고 모달은 **네이티브 dialog** 라 DOM 에 안 잡히고, `window.dialogStyle: "custom"` 은
workbench 다이얼로그용이라 이 모달에는 해당되지 않는다. **OS 스크린샷을 지나가지 않으므로
화면이 잠겨 있어도 유효하다** — 실행 시점 `IOConsoleLocked = Yes` 였다.

| 무엇을 쐈나 | `showMessageBox` 호출 | 판정 |
|---|---|---|
| **① 양성 대조** `hypeproof-studio://file/<경로>` | **0 → 1** (문구: *"An external application wants to open … Do you want to open this file or folder?"*) | 계측기가 실제로 잰다 |
| **② 본 판정** `hypeproof-studio://hypeproof.hypeproof-chat/rehearse?ticket=…` | **1 → 1** (안 늘어남) | **모달이 붙지 않는다** |

**같은 전달 경로에서 하나는 부르고 하나는 안 부른다.** 계측기가 고장나서 못 본 것이
아니라는 근거가 이것이다. ②만 재고 "안 뜬다"고 했으면 아무 뜻이 없었다.

**이 측정의 한계 둘 — 같이 읽어야 한다:**

1. **URL 을 Electron `open-url` 이벤트로 합성해서 넣었다.** macOS LaunchServices 를 거친
   **브라우저 클릭 전체 경로가 아니다.** **"브라우저 클릭까지 검증됐다"로 읽으면 안 된다.**
   이것이 추측이 아니라는 근거가 있다 — trace 로그에서 확장 authority URL 이
   `app#handleProtocolUrl(): not handled` 로 떨어지는 것을 관측했다. 즉 **합성 emit 은
   확장 URL 을 확장까지 전달하지 않는다.** 모달 판정에는 영향이 없다(모달은 이 함수 안에서
   `file`/`vscode-remote` 일 때만 검사되고, 그 앞에서 이미 갈린다 — 양성 대조가 같은 경로에서
   모달을 띄운 것이 그 증거다). 하지만 **"링크가 확장까지 닿는다"는 이 측정으로 말할 수 없다.**
2. **출하된 v0.1.56 으로 쟀다.** 그 빌드에는 우리 UriHandler 가 없으므로 이것은
   **프로토콜 라우팅을 잰 것이지 #1132 의 핸들러를 잰 것이 아니다.**

### 4.2 여기까지 오는 데 계측기가 세 번 거짓말했다

기록으로 남긴다. 처음 세 번의 관측 시도는 전부 **계측기**에서 막혔다:

- 스크린샷이 전부 검게 나왔다 — 디스플레이가 꺼져 있었다(`IOConsoleLocked = Yes`).
  **검은 화면을 "다이얼로그 없음"으로 읽었으면 정반대 결론을 자신 있게 냈을 자리다.**
- `--open-url` 로 URL 을 밀어 넣는 경로는 rc=0 인데 로그가 한 줄도 늘지 않았다.
  **rc=0 은 "전달됐다"가 아니라 "명령이 에러 없이 끝났다"일 뿐이다.**

**`--open-url` 이 왜 안 닿았는지는 아직 모른다.** 다른 수단으로 이 질문이 풀렸다고
그 원인이 밝혀진 것이 아니다.

판정 전에 `IOConsoleLocked` 를 확인하는 것을 전제 조건으로 삼는다.

| 응답만 유실된 재시도 | **일회용이되 멱등.** 5분 창 안에서는 같은 자격을 돌려준다 | §2.1 |

**위클리에서 뒤집힐 수 있다.** 뒤집히면 이 네 칸이 ⬜ 로 돌아간다.

### 5.3 다음 사람에게 남기는 수단과 함정

- **모달·메인 프로세스 동작을 재려면** Playwright `_electron` + `app.evaluate()` 로
  `dialog.showMessageBox` 를 가로챈다(§4.1). **OS 스크린샷을 안 지나가므로 화면이 잠겨 있어도
  된다.** 화면 판정 전에 `IOConsoleLocked` 를 먼저 확인한다.
- **함정 — `app.emit('open-url', …)` 로는 확장까지 못 간다.** 확장 authority URL 은
  `handleProtocolUrl(): not handled` 로 떨어진다(관측함). **위 3번(다중 창 수신)과 "링크가
  확장까지 닿는가"는 이 방법으로는 못 잰다** — 실제 브라우저 클릭이 필요하다.
- **함정 — `--extensionDevelopmentPath` 로 확장을 얹으려면 `engines.vscode` 를 `^0.1.0` 류로
  적어야 한다.** 이 앱은 `vscode.version` 으로 HypeProof 릴리스 버전(`0.1.56`)을 돌려주므로
  `^1.x` 는 semver 에서 떨어지고, `*` 도 *"not specific enough … For vscode versions before
  1.0.0"* 로 거부된다(둘 다 관측함). 관련: **#741** — 그 이슈는 **수정 코드 대신 기존 built-in
  이 로드돼 검증을 오인할 수 있다**고 경고한다. **확장이 실렸는지를 먼저 확인하고 판정한다.**
- `--open-url` 은 rc=0 이면서 인스턴스에 안 닿은 적이 있다. **원인은 아직 모른다.**

**셋 다 첫 회차를 막지 않는다.**

## 6. 이 문서가 주장하지 않는 것

- 구현 완료를 주장하지 않는다. 앱 쪽 수신부는 #1132 에 있고 **Service 쪽 교환 엔드포인트는
  아직 없다.**
- §2 의 문구들은 **앱에 들어가 있고 테스트로 고정돼 있지만**, 실제 교환 경로를 한 번도
  왕복해 본 적이 없다.
- §4 는 실측이지만 **브라우저 클릭 전체 경로를 검증한 것이 아니고**(합성 `open-url`),
  **#1132 의 핸들러를 검증한 것도 아니다**(출하 빌드 기준). 그 둘은 아직 미확인이다.
- 🅡 로 표시한 네 결정은 **Router 가 근거와 함께 내린 것이고 Jay 검토 전**이다. 제품 오너의
  확정이 아니다 — 위클리에서 뒤집히면 해당 칸은 ⬜ 로 돌아간다.
